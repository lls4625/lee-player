# 雷 player 后台播放竞品策略与可靠修复方案

## 1. 结论先行

针对上一轮确认的 `media_kit/libmpv` 后台播放中断风险，成熟且可靠的修复方向不是“让完整视频播放器继续在后台运行”，也不是“切后台就把整个 Player 暂停”，而是：

> **保留同一个播放会话和音频时钟；普通后台模式停止视频解码/渲染并拆除 GPU 输出，仅继续音频；回到前台后以有序、可撤销的状态迁移恢复视频输出。PiP、投屏等确实需要后台画面的模式单独处理。**

该策略同时符合 Apple 平台约束、Infuse 的产品定义，以及 VLC 的服务化播放器设计。它能直接消除当前最高风险的“后台 OpenGL ES 调用”链路，并降低后台 CPU、耗电和被系统终止的概率。

建议分两阶段落地：

1. **P0 稳定性修复**：新增统一的后台渲染状态机；后台关闭视频轨并 Dispose 行内输出；插件原生层增加后台 GPU 硬闸；后台轮询降频；失败时宁可暂停也不能继续提交 GPU。
2. **P1 完整性增强**：统一普通后台与 PiP 的输出所有权；完善中断恢复和可观测性；建立真机手工验收矩阵与灰度指标。

本次只给出产品与技术方案，没有修改源码，也没有执行构建或测试。

## 2. 当前问题与修复目标

### 2.1 当前情况

当前 `media_kit` 路径在前台创建 `VideoController` 后：

- Flutter 生命周期进入非 `resumed` 时仅取消“尚未完成”的附件创建，已有 `controller` 不会拆除：`v3/lib/media_kit_playback.dart:63-74`。
- `Video` 显式使用 `pauseUponEnteringBackgroundMode: false`：`v3/lib/playback_page.dart:1168-1177`。
- iOS 插件仍可能执行 `EAGLContext.setCurrent`、`glBindFramebuffer`、`mpv_render_context_render`、`glFlush`：`v3/third_party/media_kit_video/ios/Classes/plugin/TextureHW.swift:149-184`。
- 更新回调没有 App 状态闸门，会继续调用 `texture.render(size)`：`v3/third_party/media_kit_video/common/darwin/Classes/plugin/VideoOutput.swift:144-177`。
- 250 ms 心跳仍在后台完整读取 17 个 mpv 属性：`v3/lib/media_kit_playback.dart:426`、`:933-950`、`:1159-1181`。

上一轮报告已保存于：`docs/vibe/2026-10-15_10-32-19-后台播放中断独立深度排查.md`。

### 2.2 修复目标

必须同时满足以下目标，缺一不可：

1. 用户开启“后台播放”后，锁屏或切换 App，音频连续播放。
2. 普通后台模式不再产生 OpenGL/Metal/Flutter Texture 帧提交。
3. 回到前台后恢复原视频轨、尺寸、播放位置、倍速、音轨、字幕和播放/暂停意图，不重新打开媒体。
4. 用户关闭“后台播放”时，进入后台应暂停，返回前台不得擅自恢复。
5. PiP、AirPlay/外接屏与普通后台音频不能争用同一视频输出。
6. 来电、Siri、耳机拔出、媒体服务重置等系统事件继续遵循 iOS 规则。
7. 任意竞态或恢复失败不得导致旧会话覆盖新会话，也不得为了保音频而冒险在后台继续调用 GPU。

## 3. 同类产品与平台策略

### 3.1 Infuse：把能力定义为“后台音频”，并交给用户显式控制

Firecore 官方将该能力称为 **Background (audio) playback**，其描述是“视频的音频在使用其他 App 或设备锁定时继续播放”。这不是“后台继续渲染视频”，产品边界非常清楚。Infuse 历史版本加入了专门设置，近年的发布记录也持续修复“Background Playback setting”和“background audio”问题，说明它被当作独立、长期维护的播放模式，而非一次性的生命周期补丁。

可借鉴策略：

- 设置文案明确告诉用户后台只保留音频。
- 后台能力是用户策略，不与 PiP 混为一谈。
- 背景播放问题独立回归，不能仅靠普通播放测试覆盖。

官方资料：

- <https://firecore.com/blog/infuse-34-folders-folders-folders>
- <https://firecore.com/releases>

### 3.2 VLC for iOS：播放服务独立于播放器页面，生命周期在服务层统一处理

VLC 官方 iOS 源码使用全局 `VLCPlaybackService` 持有播放器、列表、音频会话通知、前后台通知、远程播放状态和视频输出，而不是让播放器页面成为会话所有者。其源码明确：

- 监听音频路由、中断、`willResignActive`、`didEnterBackground`、`willEnterForeground`。
- 注释说明必须知道何时进入后台，以停止视频、避免崩溃。
- 当“后台继续音频”设置关闭时暂停并记录是否应在回前台恢复。
- 保存进入后台前的视频输出容器，前台时重新挂回。
- PiP/外接渲染单独判断，不走普通后台暂停策略。
- 后台播放也可作为不打开 UI 的独立 App Intent。

可借鉴策略：

- **播放会话的生命周期高于页面生命周期**。
- **视频输出是可拆卸资源，播放器和队列不是**。
- **普通后台、PiP、投屏是不同渲染所有权模式**。
- **是否恢复播放取决于进入后台前的意图，而不是当前某一个异步回调的瞬时状态**。

官方源码：

- <https://github.com/videolan/vlc-ios/blob/master/Sources/Playback/Control/VLCPlaybackService.m>
- <https://github.com/videolan/vlc-ios>

### 3.3 nPlayer：能力丰富不等于后台链路天然可靠

nPlayer 的 App Store 官方页面强调多格式、硬件加速、网络播放、音轨和投屏能力，但未给出像 Infuse 那样清晰的后台音频行为契约。其当前商店评价中仍有“锁屏后扬声器停止、连接 AirPods 时正常”的用户报告。

这条评价只能作为风险信号，不能当作官方实现证据。它反而说明：后台播放不能只验证“某一种耳机、某一种路由能播”，必须覆盖内置扬声器、蓝牙、有线耳机和路由切换。

产品页面：

- <https://apps.apple.com/us/app/nplayer/id1116905928>

### 3.4 Apple：后台可以继续音频，但后台 GPU 工作是红线

Apple 的平台规则给出了技术边界：

- 音频播放 App 应使用 `AVAudioSession` 的 `.playback` 类别，并启用 Audio/AirPlay/PiP 后台能力。
- 音频中断结束后，只有在中断前正在播放、产品允许恢复、系统建议恢复时才继续。
- 耳机/蓝牙等旧输出消失时，典型媒体 App 应暂停，避免突然从扬声器外放。
- 媒体服务重置后需重建音频对象和会话，不应擅自自动播放，等待用户动作更安全。
- App 进入后台前必须停止 OpenGL ES 动画并排空命令；后台调用 OpenGL ES 可能导致系统终止。
- 后台过度 CPU 使用可能触发 `EXC_RESOURCE / CPU_FATAL`。

官方资料：

- <https://developer.apple.com/documentation/avfoundation/configuring-your-app-for-media-playback>
- <https://developer.apple.com/documentation/AVFAudio/handling-audio-interruptions>
- <https://developer.apple.com/documentation/avfaudio/responding-to-audio-route-changes>
- <https://developer.apple.com/documentation/avfaudio/avaudiosession/mediaserviceswereresetnotification>
- <https://developer.apple.com/library/archive/documentation/3DDrawing/Conceptual/OpenGLES_ProgrammingGuide/ImplementingaMultitasking-awareOpenGLESApplication/ImplementingaMultitasking-awareOpenGLESApplication.html>
- <https://developer.apple.com/library/archive/documentation/Performance/Conceptual/EnergyGuide-iOS/WorkLessInTheBackground.html>

## 4. 推荐的产品策略

### 4.1 用户可见行为

| 模式/操作 | 推荐结果 |
|---|---|
| 后台播放开启，锁屏或切 App | 视频画面停止，音频与队列继续，锁屏控制可用 |
| 后台播放关闭，锁屏或切 App | 暂停；回前台仍保持暂停，除非用户主动播放 |
| 主动开启 PiP | PiP 继续画面和音频；不进入“纯后台音频”模式 |
| AirPlay/外接屏正在播放 | 由外部渲染模式持有输出，不拆除其输出 |
| 来电/Siri 等中断 | 立即暂停；结束后按 `shouldResume`、用户设置和原播放意图共同决定是否恢复 |
| 拔耳机/蓝牙意外断开 | 暂停，不自动切扬声器 |
| 回前台恢复视频失败 | 音频继续；UI 显示“视频画面恢复失败，可重试”，不把整个会话判死 |
| 后台迁移无法在截止时间内确认 | 保守暂停，避免后台 GPU 违规 |

建议把现有“后台播放”说明改为类似：

> “锁屏或使用其他 App 时继续播放视频中的音频。画中画不受此设置影响。”

这能减少用户把“后台播放”理解成后台继续显示/渲染视频。

### 4.2 产品默认值

若当前版本已经默认开启后台播放，不建议在修复中顺便更改默认值，以免扩大产品行为变化。先保持现有默认策略，只修复执行方式；是否调整默认值应作为独立产品决策。

## 5. 推荐技术方案

### 5.0 两条播放线必须分开处理

本方案中的 `vid=no → VideoOutputManager.Dispose → Create → texture ready → 恢复 vid` **只适用于 `media_kit/libmpv` 播放线**，不适用于 AVPlayer。两条线只共享“后台播放是否允许、用户播放意图、音频会话、中断和路由”等上层产品策略，不共享视频输出生命周期实现。

```text
统一产品策略层
  ├─ 后台播放开关 / 播放意图 / AVAudioSession / 中断 / 路由 / 锁屏控制
  │
  ├─ AVPlayer 原生线（常规 MP4/MOV/M4V 等）
  │    ├─ AVPlayer + AVPlayerItem + AVPlayerLayer
  │    ├─ audiovisualBackgroundPlaybackPolicy = continuesIfPossible
  │    ├─ 普通后台保留健康的 presentation 绑定
  │    └─ didBecomeActive 时 ensureAVPlayerPresentation
  │
  └─ media_kit/libmpv 线（MKV/WebM/FLV/AVI/TS 等及 AVPlayer 失败回退）
       ├─ media_kit Player + VideoController + Flutter Texture/OpenGL
       ├─ 普通后台保存 vid、vid=no、Dispose 原生 VideoOutput
       └─ 前台 Create、确认新 texture、恢复 vid、确认非零尺寸
```

AVPlayer 当前已有独立恢复路径：`PlaybackService.swift` 为 AVPlayer 设置 `.continuesIfPossible`，普通前后台转换保留健康的 layer 绑定，并在 `didBecomeActive` 调用 `ensureAVPlayerPresentation`。这条线不应引入 `vid`、media_kit MethodChannel 或 `VideoOutputManager` 调用。

需要特别注意：格式只是初始路由依据。普通 MP4 若 AVPlayer 打开失败并回退到 media_kit，从回退成功开始，该会话就必须遵循 media_kit 的输出状态机；不能再按扩展名走 AVPlayer 的前台恢复逻辑。实现判断必须依据当前 engine 身份，而不是文件扩展名。

### 5.1 建立唯一的渲染所有权状态机

以下状态机专用于 `media_kit/libmpv` 的行内输出所有权。不要继续用多个布尔值分别描述其生命周期、PiP 和输出拆卸：

```text
foregroundInline
    | inactive / willResignActive
    v
detachingInline
    | vid=no + Dispose 确认
    v
backgroundAudioOnly
    | resumed + 可见帧
    v
restoringInline
    | Create + texture ready + 恢复 vid
    v
foregroundInline

foregroundInline --用户启动 PiP--> handingOffToPiP --> pipOwned
pipOwned --停止 PiP且前台--> restoringInline
pipOwned --停止 PiP且后台--> backgroundAudioOnly
```

每次迁移都必须携带：

- `engineId`：当前媒体会话。
- `transitionGeneration`：当前生命周期/渲染迁移代次。
- `requestId`：PiP 或输出创建请求。
- `desiredPlayback`：用户最后的播放/暂停意图。
- `savedVideoTrack`：进入纯音频前实际选中的 `vid`。

任何异步结果只有在以上标识仍匹配时才能提交。旧回调只做本地清理，不能改变当前会话。

### 5.2 P0：后台前按顺序关闭视频管线

在 `inactive/willResignActive` 开始迁移，不要等 Flutter 已完全 `paused` 后才处理。推荐顺序：

1. 冻结新的行内输出创建，增加 generation。
2. 如果 PiP 或外接渲染正持有输出，则交给相应所有者，不执行普通后台拆卸。
3. 记录当前 `vid`，若为 `no/auto/空` 则规范化保存为可恢复值。
4. 设置 `vid=no`，停止新视频解码帧进入输出。
5. 调用 `VideoOutputManager.Dispose(handle)` 并等待确认。
6. 原生渲染队列执行 barrier；OpenGL 路径在后台前完成必要的 `glFinish`/资源清理。
7. **保留当前 `VideoController` 实例**，只把其原生 VideoOutput 标记为已拆除；UI 依据渲染状态显示占位层。当前恢复代码要求已有 controller 才能执行 Create，若在这里直接置空而没有完整的新 controller 重建流程，会重新引入“回前台只有声音、没有画面”。同时保留同一个 `Player`、媒体、位置、音轨、速率和播放意图。
8. 转入 `backgroundAudioOnly`，音频继续。

当前 PiP 已在 `v3/lib/media_kit_playback.dart:503-530` 实现“记录视频轨 → `vid=no` → Dispose”的大部分原语。应抽成公共的 `InlineVideoOutputCoordinator`（命名可调整），供 PiP 和普通后台共同调用，不能复制第二套近似逻辑。

#### 为什么顺序不能反过来

- 先 Dispose、后 `vid=no`，mpv 仍可能在销毁窗口提交新帧。
- 只把 Flutter Widget 移除，原生 mpv render callback 仍可能存活。
- 只设 `vid=no` 不 Dispose，OpenGL context/texture 仍由插件持有，且异步回调可能已排队。
- 先把整个 Player pause/stop，会破坏后台音频产品目标和队列连续性。

### 5.3 P0：原生插件增加不可绕过的后台 GPU 硬闸

Dart 状态机是主控制面，但不能作为唯一安全保障。App 生命周期通知、MethodChannel 和 mpv worker 分属不同队列，始终存在窄竞态。

应在插件原生层增加第二道防线：

1. `VideoOutput` 维护原子的 `renderingAllowed`/generation。
2. 在 `UIApplication.willResignActiveNotification` 最早阶段将其置为 false。
3. `_updateCallback()` 在 resize、render、`textureFrameAvailable` 前分别检查 `disposed && renderingAllowed && generation 匹配`。
4. 已排队 worker 在闸门关闭后直接丢弃帧，不触碰 EAGLContext。
5. `didBecomeActive` 不自动打开闸门；只有 Dart 完成新输出 Create 并确认当前 generation 后才允许渲染。

这是 fail-safe：即使 Dart 的 Dispose 超时，后台也不会继续提交 GPU。Apple 的规则约束的是最终原生 GPU 行为，因此安全闸必须落在原生渲染边界。

### 5.4 P0：前台恢复不重开媒体

返回前台后的推荐顺序：

1. 等待 `resumed` 且至少一个可见帧，确认页面和 Flutter texture registry 可用。
2. 使用保留下来的当前 `VideoController`，对当前 handle 调用 `VideoOutputManager.Create`；若未来决定销毁 controller，则必须先新增并验证完整的 controller 重建与 Widget 重新绑定流程，不能只把引用设回非空。
3. 等待新 texture ID，确认它不同于拆除前的 texture ID。
4. texture ready 后恢复原 `vid`，再等待非零画面尺寸；只有这两项都确认后才恢复插件 `renderingAllowed` 并进入 `foregroundInline`。
5. 清除保存状态；如果任一步失败，保持 `backgroundAudioOnly`/前台音频降级状态并允许重试，不能伪装成恢复成功。

不得执行：重新 `open`、重新 seek、重建 Player、强制 `play`。这些操作会引入音频断点、进度跳动，以及“用户已暂停却被恢复”的错误。

若 Create 或 texture ready 失败：保持 `vid=no` 和音频播放，前台 UI 提供一次显式重试；不要把 `_failure` 设成会封锁 pause 之外所有命令的致命媒体错误。

当前代码已有可复用的防回归基础：`_createVideoOutput` 会要求 controller 存在、限制只能在前台 Create、等待新 texture ID、恢复保存的 `vid`，并继续等待非零尺寸；`_deferPiPVideoOutput` 还处理了 Flutter 与原生前台通知先后不确定的竞态。普通后台恢复应复用这些门槛，而不是另写一个只调用 Create 或只恢复 `vid` 的简化版本。

### 5.5 P0：后台心跳改为轻量模式

当前 250 ms × 17 属性约等于每秒最多 68 次 mpv 属性读取，另有每秒 4 次 Dart→Swift 快照。这不是维持音频所必需的。

推荐：

- 前台保持现有 250 ms UI 快照。
- 后台改为事件驱动优先；若短期内无法事件化，降为 1 秒一次的最小快照。
- 最小快照只读取：`time-pos`、`duration`、`pause`、`eof-reached`、`paused-for-cache` 和必要的错误状态。
- 后台禁止读取 `current-vo`、帧丢弃、`avsync` 等视频诊断属性，也不启动视频解码恢复。
- 生命周期回前台后立即执行一次完整快照，再恢复 250 ms。

锁屏 Now Playing 的流畅度不依赖 4 Hz 属性全量轮询；可以用已知 position、rate 与时间戳由系统推算，只在状态变化或约 1 秒节拍更新。

### 5.6 P1：中断恢复使用“播放意图”而不是“回调时状态”

维护独立字段：

- `desiredPlayback`：用户最后明确的 Play/Pause 意图。
- `wasPlayingBeforeInterruption`：中断开始前是否实际播放。
- `interruptionGeneration`：过滤陈旧结束通知。
- `resumeAllowedBySystem`：系统 `shouldResume` 或新 SDK 的恢复建议。

仅当四个条件同时成立时自动恢复：

1. 中断开始前正在播放；
2. 用户设置允许“中断后继续”；
3. 用户没有在中断期间主动暂停/切换项目；
4. 系统建议恢复且音频会话激活成功。

现有 0.25/0.75/1.5 秒有界重试可以保留为第一层，不建议改成无界重试。重试耗尽后保留 `desiredPlayback`，锁屏用户再次按 Play 应开启新一轮恢复，而不是沿用已耗尽的旧 generation。

### 5.7 P1：区分失败等级

建议把当前笼统失败拆为：

| 等级 | 示例 | 行为 |
|---|---|---|
| 会话致命 | 文件打不开、解码器无法建立且无音轨 | 停止并显示错误 |
| 视频输出可恢复 | texture Create/恢复失败 | 音频继续，前台提示重试画面 |
| 暂时性音频恢复失败 | 中断结束后 session 激活失败 | 有界重试，之后等待用户 Play |
| 策略性暂停 | 后台播放关闭、耳机拔出 | 正常暂停，不记录为错误 |
| 安全降级 | 后台拆卸未确认 | 暂停，记录安全原因，不冒险调用 GPU |

这能避免“画面恢复失败”反过来切断本来正常的后台音频。

## 6. 不推荐的方案

1. **只把 `pauseUponEnteringBackgroundMode` 改成 true**：虽然可能减少崩溃，但会直接违背已开启的后台音频需求，且无法证明原生输出已安全拆除。
2. **只在 Dart 中 `controller = null`**：Widget 消失不等于原生 Texture 和 mpv render context 已销毁。
3. **只设置 `vid=no`**：无法消除已经排队的 render callback 和原生资源所有权问题。
4. **后台继续完整视频解码，渲染回调里简单 return**：比当前安全，但仍浪费解码、CPU 和电量；应作为原生保险，而不是主策略。
5. **回前台重新打开媒体再 seek**：容易出现听感断点、位置误差、重复触发 EOF/连播、音轨字幕丢失。
6. **无限重试 AVAudioSession**：会与其他 App 或系统音频持续争用，不符合系统恢复建议。
7. **普通后台和 PiP 各写一套 Dispose/Create 逻辑**：极易出现双 Dispose、错误恢复旧 texture、后台误 Create 等竞态。

## 8. 手工验收方案

按项目规则，本次不执行自动测试。实现后应由用户在真机手工验证，至少覆盖：

### 8.1 核心对照

| 场景 | 样本 | 预期 |
|---|---|---|
| 前台已出画面后锁屏 | 有声 MKV/WebM | 音频连续；无 GPU 后台终止；解锁恢复画面 |
| 前台已出画面后 Home | 有声 MKV/WebM | 同上 |
| 后台直接打开下一集 | media_kit 视频队列 | 不等待 Flutter 帧；音频继续；回前台才建输出 |
| AVPlayer 对照 | MP4/MOV | 行为不回退 |
| 纯音频对照 | MP3/M4A/Ogg/Opus | 连续播放，无视频输出创建 |

### 8.2 用户操作竞态

- 锁屏瞬间按锁屏 Play/Pause。
- 拖动进度条未松手即锁屏。
- 自动切下一集的瞬间锁屏。
- PiP 启动、停止、失败回滚期间切前后台。
- 回前台恢复 texture 过程中再次锁屏。
- 后台时切换播放项目、倍速、音轨。

### 8.3 音频和系统事件

- 内置扬声器、有线耳机、AirPods、蓝牙音箱分别运行 30 分钟。
- 来电接听/拒接、Siri、闹钟、导航播报、其他播放器抢占。
- 耳机拔出与蓝牙意外断开必须暂停；控制中心主动切换输出单独验证。
- 网络抖动、NAS 断开重连、HTTP 缓冲。
- iOS 当前发布最低版本、主流版本和最新版本各验证一台真机。

### 8.4 通过标准

- 普通后台 30–60 分钟无意外停播。
- Xcode/Organizer 无后台 GPU/OpenGL、watchdog、`EXC_RESOURCE CPU_FATAL` 或 jetsam 相关终止。
- 回前台画面恢复不重开媒体，听感无明显断点，位置误差不超过一次 UI 刷新周期。
- 用户主动暂停、后台播放关闭、中断期间切换项目时绝不误恢复。
- 视频输出恢复失败时音频仍可控，重新进入页面或显式重试可恢复画面。

## 9. 灰度与回滚建议

1. 用内部开关控制新的 `backgroundAudioOnly` 路径，首版保留一键回退到“进入后台直接暂停”的安全策略。
2. 记录匿名计数而非媒体 URL：后台迁移开始/成功/超时、原生闸丢弃帧数、前台恢复成功/失败、音频中断重试结果、进程终止原因。
3. 灰度观察“后台 5/30 分钟仍活跃率”“回前台画面恢复率”“用户主动暂停后误恢复率”。
4. 若 Dispose 或恢复失败率异常，回滚应选择“暂停播放”，不能回滚到“后台保留 GPU 输出”。

## 10. 风险与注意事项

- 最大实现风险不是 `vid=no` 本身，而是普通后台与 PiP 对输出的并发所有权；必须先统一状态机再接生命周期。
- Flutter `inactive` 也会由控制中心、通知中心等短暂触发。GPU 闸应尽早关闭，但是否最终保持音频/暂停应在 `paused/didEnterBackground` 与产品设置确认后决定；短暂 inactive 返回时可快速恢复行内输出。
- 后台拆卸可能造成回前台首帧略慢，这是可接受的稳定性换取；不应为追求零首帧延迟保留后台 OpenGL context 工作。
- 上游 `media_kit_video` 升级时必须重新审查本地插件补丁，防止接口变化导致安全闸失效。
- 新 SDK 的 `resumptionRecommendationNotification` 目前应作为兼容性研究项，不应在未确认部署目标前替换现有 `shouldResume` 路径。
