# 双录屏黑框综合排查与兼容修复方案

## 一、最终结论

综合两段真机录屏、两张问题截图和当前源码后，黑色矩形不是一个已经正常建立的 iOS 画中画窗口，也不是普通 Flutter 页面长期残留。它是雷player返回主屏幕时，iOS 正在合成 App 窗口、Flutter 平台视图与 AVPlayer 视频呈现层的过渡画面；当前代码在 `willResignActive` 阶段同时销毁预创建的 PiP 控制器并执行 `videoLayer.player = nil`，使原生视频呈现层在系统动画完成前变成黑色，最终形成短暂的黑色“幽灵层”。

第二段录屏进一步说明：黑框的宽高比会跟随正在播放的媒体可见区域。`test01.mp4` 对应竖向黑框，`test02.mp4` 对应横向黑框。这不是实际 PiP 已成功启动的证据，而是 AVPlayerLayer/平台视图在系统过渡合成中的几何形态不同。

最兼容当前功能的解决方向是：

> 普通 App 失活或返回主屏幕时，不改变行内 AVPlayer 的显示拓扑——不释放 prepared PiP 控制器，不解绑 `AVPlayerLayer.player`；继续依靠 `canStartPictureInPictureAutomaticallyFromInline = false`、显式用户授权和 delegate 拒绝来禁止自动 PiP。原有完整清理逻辑只保留给真正的 PiP 启动失败、停止、媒体替换和引擎释放场景。

这比“失活时仍销毁 PiP 控制器、只保留视频层”的前一版初步方案更稳妥，因为第二段录屏提示 PiP 控制器和 AVPlayerLayer 的生命周期也不应在系统主屏幕动画开始时被重组。

## 三、为什么它不是正常的系统画中画窗口

### 1. 控件样式不符合系统 PiP

黑框中的锁定、旋转、隐藏控件是 `v3/lib/playback_page.dart` 中雷player自己的 Flutter 控件。iOS PiP 窗口不会显示这一组 App 自定义按钮。

### 2. 出现时机属于 App 主屏幕过渡

黑框与 App 窗口缩回雷player图标的动画连续发生，并在系统动画结束后消失；正常 PiP 会在主屏幕上作为可交互浮窗持续存在。

### 3. 当前业务代码没有授权这次 PiP

当前 AVPlayer PiP 只有用户点击按钮后才会设置 `avPlayerPiPAuthorized = true`。录屏所示流程是直接返回主屏幕，没有画中画按钮请求，因此即使 AVKit 产生了准备或过渡行为，也会被现有未授权拒绝逻辑停止，不属于成功的业务 PiP 会话。

### 4. 横竖差异来自媒体呈现几何

播放页的 AVPlayerLayer 使用 `.resizeAspect`，横向媒体在竖屏页面中显示为横向可见区域，竖向媒体则形成竖向可见区域。系统过渡期间原生平台视图和视频层可能独立参与合成；视频帧被解绑后，黑色底层以对应几何形态暴露，所以两段视频出现不同方向的黑框。

## 四、当前代码中的完整触发链

### 1. 播放页面使用 Flutter 平台视图承载 AVPlayerLayer

`v3/lib/playback_page.dart`：

```dart
UiKitView(key: videoKey, viewType: 'lei.player/video')
```

其上叠加雷player自己的标题、锁定、画中画、旋转、隐藏控件和进度控制。

### 2. 原生视频底板为黑色

`PlayerSurface` 直接使用 `AVPlayerLayer` 作为根图层，并设置：

```swift
backgroundColor = .black
```

因此一旦 `videoLayer.player` 被清空，平台视图仍存在，但内容立即变为黑色。

### 3. 普通播放时就预创建 PiP 控制器

`attachAVPlayerPresentationIfAllowed()` 在绑定播放器后会调用 `prepareAVPlayerPiP()`。因此用户没有点击画中画按钮时，系统中也已经存在一个以当前 AVPlayerLayer 为源的 `AVPictureInPictureController`。

这种预创建本身符合 Apple 对自定义播放器通过 KVO 观察 `isPictureInPicturePossible` 的常见做法，问题不在“存在控制器”，而在返回主屏幕动画开始时又同步销毁控制器并解绑它所引用的 player layer。

### 4. `willResignActive` 同时重组 PiP 和显示层

当前监听：

```swift
UIApplication.willResignActiveNotification
  -> suspendAVPlayerPresentationForBackground(lifecycleTransition: true)
```

随后：

```swift
discardAVPlayerPiP()
videoLayer.player = nil
avPlayerPresentationDetachedForBackground = true
```

这三步都发生在 App 仍参与主屏幕过渡动画的阶段。

### 5. 回到 App 后才重新绑定

`didBecomeActiveNotification` 到达后才调用 `restoreAVPlayerPresentationAfterBackground()`。系统展开动画可能已开始，所以重新进入 App 时同样可能先看到黑色视频层，再恢复真实画面。

## 五、完整且兼容当前功能的推荐修复

### A. 普通生命周期不再销毁呈现拓扑

移除 `willResignActive` 对 `suspendAVPlayerPresentationForBackground(lifecycleTransition: true)` 的调用，或将其替换为只记录生命周期、不改变 PiP 控制器和 `AVPlayerLayer` 的处理函数。

普通返回主屏幕时禁止执行：

- `discardAVPlayerPiP()`；
- `videoLayer.player = nil`；
- `avPlayerPresentationDetachedForBackground = true`。

这样 iOS 完成缩放和快照时仍能取得稳定的最后一帧及稳定的原生视图层级。

### B. 保留现有禁止自动 PiP 的三层保护

以下逻辑保持不变：

1. `canStartPictureInPictureAutomaticallyFromInline = false`；
2. 只有用户点击画中画按钮后才设置 `avPlayerPiPAuthorized = true`；
3. `pictureInPictureControllerWillStartPictureInPicture` 继续调用 `rejectUnauthorizedAVPlayerPiPStart`，任何未授权启动都立即停止。

Apple 对该属性的定义就是控制 App 转入后台时是否自动从行内播放启动 PiP；当前值为 `false`，与雷player“只允许手动启动画中画”的产品规则一致。

### C. `didEnterBackground` 只处理播放策略和持久化

现有以下行为保留：

- 设置 `inBackground = true`；
- 调用 `enforcePlaybackEnvironment()`；
- 取消未完成的拖动；
- 保存播放进度。

不要在这里解绑 AVPlayerLayer。后台播放关闭时，现有策略会暂停播放器；后台播放开启时，音频按现有逻辑继续。保留对象绑定不等于后台继续显示或合成视频界面。

### D. `didBecomeActive` 改为幂等校验，而不是依赖“先拆后装”

建议提供一个幂等的 `ensureAVPlayerInlinePresentation()`：

- 仅在 `mediaKit == nil`、没有 `pendingReplacement`、没有活动 PiP 时执行；
- 如果 `videoLayer.player !== player`，才重新绑定；
- 如果 PiP 控制器缺失或不再引用当前 video layer，才重新创建；
- 已经正确绑定时不重复重建控制器。

这样即使系统或异常路径确实释放过呈现对象，回到 App 仍能恢复；正常进出主屏幕则不会发生不必要的拆装。

### E. 保留真正 PiP 结束/失败路径的完整清理

现有 `suspendAVPlayerPresentationForBackground()` 不应被全局删除。建议去掉容易误用的 `lifecycleTransition` 参数，并把它改名为更明确的职责，例如：

```text
detachInlineAVPlayerAfterPiPTerminalStateIfBackground
```

它只允许在以下路径调用：

- PiP 启动超时；
- PiP 启动失败；
- 未授权 PiP 启动被 delegate 拒绝；
- PiP 正常停止且 App 仍在后台；
- 明确的播放器/媒体输出销毁。

如果 App 已经在前台，该方法不解绑行内视频层；现有 guard 应继续保留。

### F. 避免 `attachAVPlayerPresentationIfAllowed()` 在非活动状态主动清空图层

当前方法在 App 非活动且无 PiP 时会主动执行 `videoLayer.player = nil`。建议调整为：

- 非活动状态下只 `return`，保持现状；
- 只有显式终止输出的专用方法可以清空 `videoLayer.player`。

这样可以防止其他异步回调在主屏幕动画期间间接触发相同黑框。

### G. 不修改以下已修复状态机

为避免回退此前问题，以下内容保持原样：

- `manualPiPSession` 与授权截止时间；
- `pipStartIssued` 与 8 秒启动超时；
- `pendingReplacement` 的 PiP 停止确认；
- `retiringPiP` 及迟到回调隔离；
- `pipRestoreToken`、`pipRestoreController` 的 UI 恢复校验；
- media_kit 的 `MediaKitPiPRenderer`、`pipAbort`、`pipRestore` 和输出接管；
- 后台播放、音频中断、播放意图和 seek 状态机。

## 六、为什么推荐方案不会回退已有功能

| 当前功能 | 推荐修改后的行为 |
| --- | --- |
| 普通返回主屏幕 | 行内视频层和 prepared PiP 控制器保持稳定，不出现拆装黑框 |
| 禁止自动 PiP | 继续由 `canStart... = false`、授权标记和 delegate 拒绝三层保护 |
| 用户点击 AVPlayer PiP | 继续使用已经 ready 的控制器，启动速度和 `isPictureInPicturePossible` KVO 不变 |
| 用户点击 media_kit PiP | 完全不修改该路径 |
| PiP 启动失败 | 继续执行原有 retire、撤销授权和后台输出清理 |
| PiP 正常停止 | 继续等待系统 didStop；前台恢复行内播放，后台按原规则解绑 |
| PiP 中切换媒体 | 继续由 `pendingReplacement` 等待停止确认后再替换 |
| 从 PiP 返回 App | 继续使用 restore token 校验 |
| 后台播放关闭 | `enforcePlaybackEnvironment()` 继续暂停 |
| 后台播放开启 | 音频继续，主屏幕不显示普通视频窗口 |
| 控制中心/系统弹窗导致短暂 inactive | 不再错误拆卸视频层，返回时不会重新黑一下 |

## 七、暂不推荐直接改为“点击时才创建 PiP 控制器”

按需创建 PiP 控制器可以从结构上避免普通播放持有 PiP 控制器，但当前实现依赖 `isPictureInPicturePossible` 的 KVO 状态。Apple 明确说明该属性是动态且可观察的；控制器刚创建时可能还没有变为可用。

如果直接改成点击时同步创建并立即检查，可能导致首次点击偶发报 `pip_temporarily_unavailable`。要安全实现懒创建，必须新增异步等待、请求令牌、取消、超时和生命周期重校验，修改面明显更大。

当前问题已有更小、更直接的解决点，因此建议先保留预创建控制器，只停止普通生命周期中的销毁和图层解绑。如果真机修复后仍观察到未授权 PiP 尝试，再单独评估带异步 KVO 等待的懒创建方案，不应与本次显示修复一起扩大范围。

## 八、建议增加的诊断记录

为便于实体设备确认，不改变业务行为的前提下，可在现有 `lifecycleEvents` 中记录：

- `willResignActive`、`didEnterBackground`、`willEnterForeground`、`didBecomeActive`；
- PiP `willStart`、`didStart`、`failedToStart`、`didStop`；
- 每次 `videoLayer.player` 绑定或解绑的原因；
- `avPlayerPiPAuthorized`、`pipStartIssued`、`pipActive`；
- 当前 engine、generation 和 application state。

如果修复后普通返回主屏幕过程中没有 PiP delegate 的 `willStart/didStart`，即可进一步确认黑框不是系统实际建立的 PiP。

## 九、人工验证矩阵

源码修改后由用户手动执行，建议每项连续往返至少 10 次：

1. AVPlayer 竖向 MP4，播放中返回主屏幕并重新进入；
2. AVPlayer 横向 MP4，播放中返回主屏幕并重新进入；
3. 上述两种视频在暂停状态重复测试；
4. 后台播放开启和关闭分别测试；
5. 控制中心、通知中心、系统弹窗等只导致 inactive 的场景；
6. 点击 AVPlayer 画中画，确认能正常出现、播放、暂停、关闭和返回 App；
7. 点击画中画后立即返回主屏幕，确认授权窗口和启动握手正常；
8. 连续点击画中画，确认防重复逻辑正常；
9. 画中画中切换、移动或删除当前媒体，确认停止确认栅栏正常；
10. MKV/WebM 等 media_kit 视频的普通进出主屏幕和手动画中画；
11. 音频文件后台播放；
12. 横竖屏切换后重复以上关键场景。

验收标准：

- 普通返回主屏幕不出现黑色竖框或横框；
- 未点击画中画按钮时不产生持续 PiP 窗口；
- 点击画中画按钮后功能与当前版本一致；
- 返回 App 不出现明显黑屏，也不重复创建播放器或丢失进度；
- 后台播放设置行为不变。
