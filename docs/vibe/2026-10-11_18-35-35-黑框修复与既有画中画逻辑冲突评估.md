# 黑框修复与既有画中画逻辑冲突评估

## 一、结论

黑框问题可以在不破坏此前画中画修复的前提下解决，但前提是采用“拆分普通生命周期路径”的窄范围修改，不能直接删除或整体弱化现有 `suspendAVPlayerPresentationForBackground()`。

- **直接删除该方法中的 `videoLayer.player = nil`：存在冲突风险。**该方法除普通退后台外，还被 AVPlayer 画中画启动失败、画中画停止和未授权启动拒绝路径复用。整体改变会同时改变这些异常清理路径。
- **仅让普通 `willResignActive` 改用一个“不解绑视频层、只撤销未授权预创建 PiP 控制器”的新路径：与现有修复兼容。**手动画中画授权、停止确认、恢复令牌、媒体替换栅栏以及 media_kit 输出交接均可保持原样。

因此，这不是“回滚以前的画中画修复”，而是把以前混在同一方法中的两个职责分开：

1. 阻止系统在用户未点击按钮时自动启动画中画；
2. 解绑 AVPlayer 视频呈现层。

普通返回主屏幕只需要第 1 项，不需要在系统动画开始时执行第 2 项。

## 二、现有画中画保护链路

### 1. 禁止自动画中画

当前保护并不只依赖视频层解绑，还包含：

- `AVPictureInPictureController.canStartPictureInPictureAutomaticallyFromInline = false`；
- 只有用户明确点击画中画按钮后才设置 `avPlayerPiPAuthorized = true`；
- `pictureInPictureControllerWillStartPictureInPicture` 会调用 `rejectUnauthorizedAVPlayerPiPStart`，拒绝未授权启动；
- 普通失活时可以释放仅处于 prepared 状态、尚未开始的 PiP 控制器。

建议修复会保留以上全部保护，只是不再同时把 `AVPlayerLayer.player` 清空。

### 2. 手动画中画启动保护

`startPiP` 当前使用：

- `pipRequesting` 防止重复请求；
- `manualPiPSession` 和有限授权窗口；
- `avPlayerPiPAuthorized` 标记明确的用户操作；
- `pipStartIssued` 标记正在进行的启动握手；
- 8 秒启动超时；
- `retiringPiP` 管理正在停止的控制器。

普通生命周期新路径必须继续使用以下门禁：

```swift
pendingReplacement == nil
mediaKit == nil
!avPlayerPiPAuthorized
!pipActive
```

这样用户已经点击画中画、画中画正在启动或已经活动时，返回主屏幕不会销毁该控制器。

### 3. 画中画停止和媒体替换保护

当前代码通过 `pendingReplacement`、`retiringPiP`、`finishPendingReplacement` 和 `finishRetiringPiP` 确保：

- 旧画中画停止得到系统确认前，不替换播放器或媒体输出；
- 停止超时不能被误判为安全释放；
- 迟到的回调不能恢复已经失败或被替换的会话。

这些逻辑与普通 `willResignActive` 黑框无直接关系，修复时不得调整，也不需要调整。

### 4. 从画中画恢复 App 的保护

`PlayerBridge.swift` 使用 `pipRestoreToken` 和 `pipRestoreController` 校验恢复请求，只有当前控制器和令牌匹配时才确认恢复 UI。建议修复不涉及该桥接代码，因此不会影响从画中画点回 App 的流程。

### 5. media_kit 画中画保护

media_kit 使用独立的 `MediaKitPiPRenderer`、输出接管、`pipAbort`、`pipRestore` 和恢复超时机制。黑框录屏对应 MP4 的 AVPlayer 路径，建议修复应限定在 AVPlayer 生命周期处理，不修改 media_kit 的视频输出交接。

## 三、存在冲突风险的错误改法

### 错误改法 1：全局删除 `suspendAVPlayerPresentationForBackground()` 的解绑行为

该方法还在以下场景调用：

- AVPlayer PiP 启动超时；
- AVPlayer PiP 正常停止；
- 未授权 PiP 启动被拒绝；
- PiP 启动后授权状态异常。

全局改变可能使已经停止或失败的 PiP 控制器与行内视频输出同时存在，削弱此前“一个输出所有者”的保护。

### 错误改法 2：删除 `willResignActive` 中的全部处理

这会保留 prepared 状态的 PiP 控制器。即便 `canStartPictureInPictureAutomaticallyFromInline` 已设置为 `false`，仍不应移除现有的防御性撤销与未授权 delegate 拒绝链路。

### 错误改法 3：在 `didEnterBackground` 再销毁播放器图层

这只是改变黑屏出现时机，还可能让系统后台快照变黑，并不能解决从主屏幕重新展开 App 时的视频层恢复延迟。

### 错误改法 4：改动 media_kit 输出恢复逻辑

本问题根因在 AVPlayer 的 `AVPlayerLayer` 解绑。扩大到 media_kit 会无谓影响已经建立的 native renderer 接管与恢复握手。

## 四、兼容既有修复的实施边界

建议后续实现遵循以下结构：

1. 新增一个只用于普通失活的 AVPlayer 方法；
2. 该方法沿用现有门禁，确认没有手动 PiP 授权、没有活动 PiP、没有待完成的媒体替换；
3. 只调用 `discardAVPlayerPiP()` 撤销未启动的 prepared 控制器；
4. 保留 `videoLayer.player === player`，不修改 `avPlayerPresentationDetachedForBackground`；
5. `willResignActive` 改为调用这个新方法；
6. `didBecomeActive` 在 AVPlayer 行内视频仍绑定时重新执行 `prepareAVPlayerPiP()`；
7. 原有 `suspendAVPlayerPresentationForBackground()` 保持不变，继续服务真正的 PiP 失败、停止和未授权启动拒绝路径；
8. 不修改 `pendingReplacement`、`retiringPiP`、PiP restore token、media_kit renderer 或后台播放策略。

示意职责如下：

```text
普通返回主屏幕
  └─ 撤销未启动的 prepared PiP 控制器
     └─ 保留 AVPlayerLayer.player，供系统过渡动画显示最后画面

真正的 PiP 失败 / 停止 / 非法启动
  └─ 继续走现有 suspendAVPlayerPresentationForBackground
     └─ 按原规则停止控制器并在需要时解绑呈现层
```

## 五、影响判断

| 既有功能或修复 | 按推荐边界修改后的影响 |
| --- | --- |
| 用户未点击时不得自动画中画 | 保留；prepared 控制器仍在失活时撤销，delegate 拒绝仍在 |
| 手动启动 AVPlayer 画中画 | 保留；授权和启动中的控制器不被普通失活路径撤销 |
| AVPlayer PiP 启动超时及失败清理 | 保留；原 `suspendAVPlayerPresentationForBackground()` 不改 |
| PiP 停止后恢复行内播放 | 保留；停止回调与恢复逻辑不改 |
| PiP 中切换或清理媒体的等待栅栏 | 保留；`pendingReplacement`、`retiringPiP` 不改 |
| 从 PiP 点回 App 的 UI 恢复令牌 | 保留；`PlayerBridge` 不改 |
| media_kit PiP 输出接管/恢复 | 无直接影响；相关代码不改 |
| 后台播放开关 | 策略不改；关闭时仍由 `enforcePlaybackEnvironment()` 暂停 |
| 返回主屏幕缩放动画 | 改善；视频层不再在动画开始前变黑 |

## 六、剩余风险与人工验证重点

静态分析判断推荐方案与既有画中画状态机兼容，但实体设备仍需人工覆盖以下组合：

1. AVPlayer 视频播放中连续进出主屏幕；
2. AVPlayer 视频暂停时连续进出主屏幕；
3. 后台播放开关分别开启和关闭；
4. 用户点击画中画后立即返回主屏幕；
5. 画中画已经显示时点回 App；
6. 画中画启动失败或快速重复点击；
7. 控制中心、通知中心、系统弹窗等只触发 inactive、不真正进入后台的情况；
8. media_kit 格式的视频重复上述关键流程，确认没有旁路影响；
9. 播放中切换文件、删除/移动当前文件与 PiP 停止回调交错的情况。

主要剩余风险是：后台期间保留 `AVPlayerLayer` 对播放器的引用后，需在真机观察长时间后台音频时的资源占用。但 App 进入挂起后界面不会继续参与屏幕合成，且后台播放是否继续仍由现有策略控制；该风险低于使用截图覆盖或固定延时造成的新竞态。
