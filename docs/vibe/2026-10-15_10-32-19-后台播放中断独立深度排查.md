# 雷 player 后台播放中断独立深度排查

## 1. 结论

**存在后台播放中断风险，且至少有 1 条高风险代码路径。**

当前代码的 AVPlayer 主路径已具备正确的后台音频声明、`.playback` 音频会话、后台继续策略、锁屏控制、中断与路由处理，没有发现“一切到后台就必然暂停”的通用逻辑错误。

但 MKV、WebM、FLV、AVI、TS、Ogg/Opus 等优先走 `media_kit/libmpv` 的视频，以及 AVPlayer 失败后回退到 `media_kit` 的视频，在“前台已建立视频输出后再锁屏/切后台”时，现有代码没有停止或拆除 OpenGL ES 渲染输出。它与 iOS 的后台 GPU 限制直接冲突，可能导致渲染失败、音频卡住，严重时被系统终止；用户看到的就是后台播放突然中断。

本次是静态独立审查，没有执行构建、编译、单元测试、集成测试或真机自动化验证。因此结论区分为“代码已证实存在的风险路径”与“需真机确认的触发概率”，不宣称已在设备上复现。

## 4. 发现一：`media_kit` 前台视频输出未在后台前停止（高风险）

### 4.1 修改前/当前情况

`MediaKitPlayback.didChangeAppLifecycleState` 在非 `resumed` 状态只调用 `_cancelVideoAttachment()`。该方法只取消 `_videoAttachFrame` 和完成尚未完成的 `_videoAttachReady`，不会处理已存在的 `controller`，也不会设置 `vid=no` 或调用 `VideoOutputManager.Dispose`。

`PlaybackPage` 创建 `Video` 时又显式传入 `pauseUponEnteringBackgroundMode: false`，所以插件自带的后台暂停保护也被关闭。

iOS 侧 `TextureHW` 使用 `EAGLContext`、`glBindFramebuffer`、`mpv_render_context_render` 和 `glFlush`。`VideoOutput` 在 mpv 更新回调中继续调用 `texture.render(size)`，该链路没有 App 前后台闸门。

Apple 明确要求 App 进入后台后不得提交新的 OpenGL ES 命令，后台访问 GPU 可导致 App 被系统终止：

- <https://developer.apple.com/library/archive/documentation/3DDrawing/Conceptual/OpenGLES_ProgrammingGuide/ImplementingaMultitasking-awareOpenGLESApplication/ImplementingaMultitasking-awareOpenGLESApplication.html>
- <https://developer.apple.com/documentation/uikit/preparing-your-ui-to-run-in-the-background>

### 4.2 修改后情况

本次未修改源码，所以该风险仍然存在。

### 4.3 建议修改内容

建议将“行内 `media_kit` 视频输出”与“后台音频解码/播放”分离：

1. 在 `willResignActive`/Flutter `inactive` 阶段立即停止新的渲染提交，并在进入 `paused` 前确认 GPU 工作已排空。
2. 对非 PiP 的普通后台播放，保留同一 `Player` 和播放意图，但暂时拆除视频输出并将 `vid` 设为 `no`，只播音频。
3. 返回前台后，在新的可见帧中重建输出、恢复原视频轨，不重建媒体会话、不 seek、不改变 play/pause 意图。
4. 必须与现有 PiP 的 `vid=no` / Dispose / restore 所有权状态机统一，避免两套逻辑重复拆除或错恢复输出。

### 4.4 修改原因

后台音频不需要视频 GPU 输出；留下 OpenGL ES 输出不仅浪费资源，还违反 iOS 后台执行规则。

### 4.5 可能影响与注意事项

- 变更会直接触及 media_kit PiP 输出交接，必须使用 engine ID、request ID、generation 和前后台状态多重栅栏。
- 不应通过“切后台直接 pause Player”解决，否则会破坏用户开启的后台音频。
- 恢复输出要处理“创建途中又进后台”的窄竞态；现有 `LOCAL_PATCH.md` 已承认 PiP restore Create 存在类似窗口。

## 5. 发现二：后台 `media_kit` 仍以 250 ms 周期进行重诊断轮询（中风险）

### 5.1 修改前/当前情况

`media_kit_playback.dart` 在打开后始终安装 250 ms 的 `Timer.periodic`。每次 `_refresh` 并行读取 17 个 mpv 属性，构建轨道/诊断快照，再通过 MethodChannel 发回 Swift。生命周期回调只重置计量窗口，没有在后台降频或转为只保留 EOF/故障必需信号。

这相当于最多约 68 次 mpv 属性请求/秒，外加每秒 4 次 Dart→Swift 快照。它不一定立即断播，但与后台视频解码、OpenGL 渲染叠加后，会增大发热、耗电、CPU 资源终止和长时间后台不稳定的概率。

Apple 的后台能耗指南说明，后台过量 CPU 使用可导致 `EXC_RESOURCE / CPU_FATAL` 终止：

- <https://developer.apple.com/library/archive/documentation/Performance/Conceptual/EnergyGuide-iOS/WorkLessInTheBackground.html>

### 5.2 修改后情况

本次未修改源码，该风险仍然存在。

### 5.3 建议修改内容与原因

- 后台播放时把快照降为远低于 4 Hz 的频率，或改成事件驱动；仅保留 EOF、fatal error、必要的 Now Playing 进度和远程控制确认。
- 不在后台执行视频解码器症状检测/修复；当前 Swift 端本就只允许前台解码修复。
- 前台恢复后立即补一次完整快照，保持 UI 正确。

直接影响是后台进度更新粒度可能降低；但音频连续性和系统资源安全更重要。

## 6. 发现三：音频恢复只给约 2.5 秒重试窗口（中低风险）

### 6.1 修改前/当前情况

`AudioRecoveryRetryPolicy.delays` 为 0.25、0.75、1.5 秒。如果中断结束后 `AVAudioSession.setActive(true)` 或 `media_kit` play 回执在这个窗口内持续失败，服务会进入 `audioRecovery=exhausted`，标记 `media_playback_failed`，不再自动恢复。

代码保留 `wantsPlayback=true`，用户再次显式点击 Play 可开启新一轮恢复，因此不是无法恢复的死锁；但在锁屏状态，用户的主观体验仍是“通话/语音/音频抢占结束后没继续播”。

### 6.2 修改后情况

本次未修改源码，该策略保持不变。

### 6.3 建议

先通过真机日志确认失败原因，再决定是否延长重试或等待更明确的系统“可恢复”信号。不建议无界重试，否则可能反复抢占其他 App 的音频会话。Apple 的建议是仅在中断前正在播放且系统建议恢复时自动继续：

- <https://developer.apple.com/documentation/AVFAudio/handling-audio-interruptions>

## 7. 不应当作缺陷的“后台停播”情形

下列行为是当前明确产品/系统策略，不能与随机中断混为一谈：

| 用户操作/系统事件 | 当前结果 | 判定 |
|---|---|---|
| “后台播放”关闭后切后台/锁屏 | 立即暂停，回前台仍保持暂停 | 符合设置文案 |
| 拔掉有线耳机或蓝牙音频设备断开 | 立即暂停，不自动切外放继续 | 符合 Apple 隐私建议 |
| 中断前未播放 | 中断结束不恢复 | 正确 |
| “中断后继续播放”关闭 | 通话/语音结束后不自动恢复 | 正确 |
| iOS 未给出 `shouldResume` | 不自动恢复 | 保守且符合现有产品文案 |
| 媒体服务重置 | 重建播放对象但不自动开播 | 符合 Apple 要求 |
| 睡眠定时到期 | 暂停 | 正确 |
| 关闭连播或顺序模式播到队尾 | 停止 | 正确 |
| 强制退出 App/系统因内存压力终止 | 停止 | iOS 平台限制 |
| 视频文件本身无可播音轨 | 不能依靠“后台音频”保持长时间运行 | 内容/系统能力边界 |

Apple 对耳机拔出的建议：<https://developer.apple.com/documentation/avfaudio/responding-to-audio-route-changes>

Apple 对媒体服务重置的要求：<https://developer.apple.com/documentation/avfaudio/avaudiosession/mediaserviceswereresetnotification>

## 8. 用户操作角度的重点复现矩阵

下列是建议的真机手工复现顺序，本次未执行：

1. **最高优先级：普通 `media_kit` 视频后台**
   - 后台播放开；播放有声 MKV/WebM；前台先播 30 秒，确保视频贴图已建立；然后锁屏、Home 键、切其他 GPU 重应用。
   - 分别观察 1、5、30 分钟，检查是音频暂停、App 被杀、还是回前台视频无法恢复。
2. **对照组：AVPlayer 视频**
   - 用相同时长和操作播放 MP4/MOV。如果 AVPlayer 稳定而 MKV 中断，基本可把范围收窄到 `media_kit` 输出/轮询。
3. **纯音频对照**
   - MP3/M4A（AVPlayer）与 Opus/Ogg（media_kit）各播 30 分钟。纯音频不创建 VideoController；如果纯音频稳定、有声 MKV 不稳定，更支持 GPU 输出根因。
4. **系统中断**
   - 后台播放时分别测试来电接听/拒接、Siri、闹钟、其他音频 App 抢占；对照“中断后继续播放”开/关。
5. **音频路由**
   - 有线耳机拔出、AirPods 放回盒、蓝牙远离断开、在控制中心手动改输出。前三项预期暂停，手动切路由需观察是否被过度归类为断开。
6. **操作竞态**
   - 拖动进度条未松手就锁屏；切后台瞬间按锁屏 Play/Pause；曲目结束自动切下一集时锁屏；手动 PiP 启停过程切后台。
7. **终止原因核对**
   - 不只看 UI；同时检查 Xcode Organizer/Devices 中的 termination/crash log，重点找 GPU/OpenGL 违规、`EXC_RESOURCE CPU_FATAL`、watchdog 和 jetsam。

## 9. 现有测试覆盖的证据与缺口

### 已有保护

- Swift 测试源码覆盖了中断 begin/end、`shouldResume`、恢复开关、媒体服务重置、耳机拔出、连播 EOF 竞态和新旧 play 回执竞态。
- Dart 测试源码覆盖了“在后台打开新 `media_kit` 项目时不等待视频帧”、后台 seek/control 不依赖视频表面，以及 PiP 后台恢复输出。

### 明确缺口

`v3/test/media_kit_background_open_test.dart` 文件头明确声明，这些用例不验证 decoding、physical audio、GPU rendering、AVKit 或 iOS background execution entitlement。

当前没有证据覆盖：

- 前台已建立 OpenGL ES 输出后的真机后台行为；
- 30–60 分钟后台 `media_kit` 的能耗和终止原因；
- 真实扬声器/蓝牙设备的持续输出；
- 真实通话、Siri、闹钟、导航音频中断后的恢复时序；
- iOS 17、18 及当前发布目标系统的差异。

## 10. 其他兼容性注意

当前代码仅使用 `interruptionNotification` 中的 `shouldResume`。Apple 最新 SDK 文档已把 `shouldResume` 标记为过时，并提供新的 `resumptionRecommendationNotification`，但目前文档仍带 Beta 标记。这不应在未确认最低/目标 SDK 和实机行为前直接改代码，但应列入新系统兼容性验证：

- <https://developer.apple.com/documentation/avfaudio/avaudiosession/resumptionrecommendationnotification>
