# 主页任意返回路径保持竖屏方案评估

## 验收目标

本次按以下产品目标评估：

> 无论用户在播放页做过什么操作，无论通过页面返回按钮、系统/路由返回、画中画相关流程或 App 前后台切换回到 App 主页（课程库），主页都必须保持竖屏，不显示主页横屏帧，也不在主页已显示后再播放旋转动画。

## 总体评估

上一轮建议中“播放页可横竖屏，主页固定竖屏”的方向正确，但需要区分三种实现程度：

| 实现方式 | 是否满足目标 | 原因 |
| --- | --- | --- |
| 只把 `playbackExitOrientations` 改为 `portraitUp` | 不完全满足 | 能避免录屏中的“退出后再解锁横屏”，但 `dispose()` 发生较晚且当前调用未等待；从横屏直接退出时，主页仍可能先以横屏露出再旋转。 |
| 只把顶部返回按钮改为“先竖屏、再 `pop`” | 不满足 | 只覆盖按钮，无法覆盖系统返回、边缘侧滑、程序化路由移除、画中画恢复及以后新增的退出入口。 |
| “集中退出门禁 + 主页竖屏不变量 + `dispose` 兜底” | 满足 | 可以同时保证退出时序和主页最终方向，且不依赖单一按钮入口。 |

因此，上一轮建议需按第三种完整形态实施，才能满足“用户任意操作”的要求。

## 当前必须覆盖的返回路径

### 1. 播放页显式返回按钮

`v3/lib/playback_page.dart` 第 1169 行和第 1230 行各有一个返回按钮，分别对应普通播放状态和画中画状态，当前都直接调用 `Navigator.of(context).pop()`。

这两处不应各自编写方向处理，而应共用同一个幂等的异步退出方法，避免重复点击和竞态。

### 2. 系统返回、路由返回和 iOS 边缘侧滑

`v3/lib/playback_page.dart` 第 1242–1243 行已使用 `PopScope`，但当前在未锁定控件时允许先 `pop`，然后只在 `didPop == true` 后调用 `dismissPlayer()`。该回调并没有在主页暴露前恢复竖屏。

要达成目标，返回请求必须在路由真正移除前经过统一门禁：

1. 标记正在退出，忽略重复请求。
2. 先将 App 方向限制为 `DeviceOrientation.portraitUp`。
3. 等待系统确认方向请求完成。
4. 再移除播放路由。

横屏播放时的交互还有一个必须明确的取舍：如果要绝对避免主页在侧滑过程中以横屏露出，就不能让一次未拦截的交互式侧滑直接完成路由返回。应先拦截返回意图，完成竖屏切换后再执行受控 `pop`。这可能使 iOS 原生侧滑动画不再完全连续，但是“主页永不露出横屏”的必要约束。

### 3. 画中画及原生 UI 恢复

`v3/lib/library_page.dart` 第 335–365 行可以由普通操作或画中画恢复请求打开播放页。画中画本身不应改变主页竖屏策略：

- 如果画中画运行时用户把播放页退回主页，主页仍必须立即固定竖屏，音视频的后台状态不影响页面方向。
- 如果 iOS 停止画中画时要求恢复播放 UI，可以重新打开播放页；从该页再次退出时，仍经过同一个统一退出门禁。
- 不能在“任意 `Navigator.pop`”时都恢复主页方向，因为播放页内的弹窗、菜单和播放队列也使用 `pop`；只有播放页路由本身退出才能触发主页竖屏策略。

### 4. App 前后台切换

`LibraryPage` 已是 `WidgetsBindingObserver`，并在第 276–283 行处理 `resumed`，因此可以在这里增加主页竖屏不变量的兜底。但必须以 `playerVisible == false` 为条件：`LibraryPage` 在播放路由下方仍然存活，如果每次 App 恢复都无条件锁竖屏，用户在横屏播放页切出再回来时，播放页会被错误强制为竖屏。

### 5. 冷启动和异常路由移除

`v3/lib/main.dart` 第 10–20 行目前在 `runApp` 前没有主页竖屏策略。由于 `Info.plist` 允许横屏，如果目标是 App 主页始终为竖屏，则冷启动时也应在首帧前建立竖屏策略。

同时，`dispose()` 中仍应保留 `portraitUp` 兜底，用于覆盖将来可能出现的程序化路由移除或其他未经常规退出方法的场景。该兜底不是正常返回流程的唯一保障。

## 建议的完整方向策略

### 策略一：明确页面所有权

- App 主页、设置页、法律文档页和打赏页：仅 `portraitUp`。
- 播放页：允许通过旋转按钮在竖屏与左右横屏之间切换。
- 画中画：不拥有 App 主页方向，主页是否显示决定 App 方向。

### 策略二：建立单一退出入口

播放页所有正常退出意图都进入同一个异步方法，该方法具备：

- 重入保护；
- 弹窗/底部面板与播放路由的区分；
- 先竖屏、后退出的严格时序；
- `mounted` 和路由仍为当前页的检查；
- 在方向 API 抛错时的可观测失败处理，不能像当前 `catchError` 一样完全吞掉。

### 策略三：主页独立兜底

主页至少在以下时机重申 `portraitUp`：

- App 首帧之前；
- 播放路由完成返回之后；
- App 恢复前台且当前没有显示播放页时。

这一层可以防止未来新增返回入口时遗漏方向恢复。

## 场景覆盖矩阵

| 用户场景 | 完整方案的处理 | 预期结果 |
| --- | --- | --- |
| 竖屏播放→返回按钮 | 统一退出门禁确认竖屏后退出 | 主页全程竖屏，无多余动画 |
| 横屏播放→返回按钮 | 先在播放页回竖屏，再退出 | 主页第一帧即为竖屏 |
| 横屏→点旋转回竖屏→退出 | 竖屏请求幂等，不再解锁横屏 | 不再出现本次录屏问题 |
| 未锁定状态的系统返回 | 返回意图被统一门禁处理 | 与按钮返回一致 |
| 横屏边缘侧滑 | 先拦截、回竖屏，再受控退出 | 主页不以横屏露出 |
| 控件锁定时返回手势 | 继续按现有产品逻辑拦截 | 不返回主页，方向不变 |
| 画中画中退回主页 | 播放状态与页面方向解耦 | 主页竖屏，画中画状态按原逻辑保留 |
| 停止画中画恢复播放 UI→再退出 | 恢复的播放路由使用同一退出门禁 | 主页竖屏 |
| 主页在前台→切出 App→再进入 | `resumed` 且 `playerVisible == false` 时重申竖屏 | 主页竖屏 |
| 横屏播放→切出 App→再进入 | `playerVisible == true` 时主页不抢占方向 | 仍回到原播放页方向 |
| 异常或程序化移除播放路由 | `dispose()` 的 `portraitUp` 兜底 + 主页重申 | 最终竖屏；正常路径不依赖该兜底 |

## 仍需正确理解的边界

“主页始终竖屏”不等于“退出时永远不发生任何旋转”。当用户从横屏播放页直接返回时，从横屏切回竖屏是必需过程；正确验收标准是：

- 旋转在播放页仍然是前台页时完成；
- 主页首次可见帧已经是竖屏；
- 主页显示后不再发生第二次旋转。

在 iOS/Flutter 系统方向 API 正常返回的前提下，上述完整方案可以满足用户提出的任意操作返回主页仍保持竖屏的要求。

## 影响与注意事项

- 方向控制是 App 级全局状态，不能把主页和播放页当成两个完全独立的方向容器。
- 应避免多个页面同时以 `unawaited` 方式写入方向策略，否则会再次形成“最后完成的异步请求覆盖前者”的竞态。
- 横屏状态直接退出时，需在旋转期间禁止重复退出和重复旋转操作。
- iPad 多任务/窗口化下的方向 API 受系统窗口尺寸约束，不应将 iPhone 全屏行为无条件视为 iPad 保证。如当前验收范围仅为 iPhone，建议在实施时明确限定。
- 修复后应对覆盖矩阵逐项真机手动验证，特别是横屏直接返、iOS 边缘侧滑和画中画恢复。
