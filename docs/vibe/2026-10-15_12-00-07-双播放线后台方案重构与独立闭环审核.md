# 雷 player 双播放线后台方案重构与独立闭环审核

## 1. 审核结论

### 1.1 公正结论

当前讨论中的“普通后台也执行 `vid=no → Dispose → 前台 Create`”方案，**方向正确但尚未完全闭环，不建议原样直接实施**。

它能够针对 `media_kit/libmpv` 的后台 OpenGL 风险，但存在三项关键缺口：

1. 现有 Dispose/Create 恢复链属于 PiP 输出交接流程，恢复期间会 `pauseEngine()`；普通后台需要音频连续，不能直接复用该业务层。
2. 现有 `presentationWaiting` 会禁止播放、禁止部分控制，并显示“正在等待画中画结束”；普通后台恢复若复用它，会形成新的停音和 UI 卡点。
3. 每次 `willResignActive` 都 Dispose 会覆盖控制中心、通知中心、系统弹窗等短暂 inactive 场景，容易制造黑屏、恢复延迟和高频重建。当前插件的 Dispose/deinit 自身还会进入 EAGLContext，不能拖到已经进入后台后执行。

因此，本报告将推荐方案调整为：

> **AVPlayer 维持现有原生后台策略；media_kit 普通后台采用“暂停/静默渲染（suspend/quiesce）优先、保留 VideoController 和原生输出、`vid=no` 停止视频解码”，前台原地恢复；只有原地恢复失败才在前台执行 Dispose/Create 重建。PiP 因为确实发生输出所有权转移，继续使用独立的 Dispose/Create 交接。**

该修订方案在静态逻辑上可以形成闭环，并比“普通后台每次重建 VideoOutput”更不容易复现“有声音、没画面”。但它仍需实现后进行真机手工验证，当前不能宣称已经实际解决。

### 1.2 评级

| 评估对象 | 结论 | 说明 |
|---|---|---|
| 当前未修改代码 | 不通过 | media_kit 已有行内输出在后台仍可能调用 OpenGL，根因仍在 |
| 原始 Dispose/Create 方案 | 有条件可行，但不闭环 | 能消除后台 GPU 风险，但会误用 PiP 暂停/等待语义，并有前台无画面与长等待风险 |
| 本报告修订后的双线方案 | 静态设计通过，可进入实现 | 播放、渲染、PiP、失败和用户操作均有独立状态与出口；仍需真机验证触发率和插件行为 |

## 3. 当前真实架构：统一策略、两条播放线

```text
用户与统一播放服务 PlaybackService
  ├─ 后台播放开关
  ├─ wantsPlayback（用户播放意图）
  ├─ AVAudioSession / 中断 / 路由 / 锁屏控制
  ├─ 队列 / EOF / 睡眠定时 / 进度记录
  │
  ├─ 播放线 A：AVPlayer
  │    ├─ 常规 MP4/MOV/M4V 等优先进入
  │    ├─ AVPlayer + AVPlayerItem + AVPlayerLayer
  │    └─ AVKit PiP
  │
  └─ 播放线 B：media_kit/libmpv
       ├─ MKV/WebM/FLV/AVI/TS/Ogg/Opus 等优先进入
       ├─ AVPlayer 打开失败后的回退也进入此线
       ├─ Dart Player + VideoController
       ├─ Flutter Texture + iOS OpenGL 输出
       └─ 自建 AVSampleBufferDisplayLayer PiP
```

两条线共享产品决策，不共享视频输出实现。判断当前恢复路径必须依据实际 engine 身份，不能依据扩展名：一个 MP4 在 AVPlayer 失败并回退后，也必须走 media_kit 状态机。

## 4. 统一产品策略

### 4.1 用户契约

| 场景 | 预期行为 |
|---|---|
| 后台播放开启，锁屏或切 App | 继续播放音频，不自动启动 PiP |
| 后台播放关闭，锁屏或切 App | 暂停，回前台保持暂停 |
| 用户手动启动 PiP | PiP 可在后台继续画面和音频 |
| 来电/Siri 中断 | 暂停；结束后仅在用户设置允许、此前在播且系统建议恢复时继续 |
| 耳机/蓝牙意外断开 | 暂停，不自动切扬声器外放 |
| 画面恢复失败 | 音频和锁屏控制继续可用；前台明确提示并允许重试画面 |
| 无音轨视频进入后台 | 不能伪装成后台播放成功；暂停并给出可理解提示 |

设置文案应明确“继续播放音频”。当前部分文案已明确音频，但设置主说明仍使用“继续播放”，建议统一，避免用户误以为普通后台会继续视频画面。

### 4.2 统一状态只负责什么

统一层只负责：

- `engineKind = avPlayer | mediaKit`
- `wantsPlayback`
- `backgroundEnabled`
- `appPhase = active | inactive | background`
- `audioInterruption`
- `audioRoute`
- `pipOwnership`
- 当前 `generation/session/operation`

统一层不应直接假定两种引擎使用相同的输出恢复命令。

## 5. 播放线 A：AVPlayer 策略

### 5.1 当前已有的正确基础

- 设置 `AVPlayer.audiovisualBackgroundPlaybackPolicy = .continuesIfPossible`。
- 使用 `.playback / .moviePlayback` 音频会话。
- `Info.plist` 已声明 `UIBackgroundModes = audio`。
- 普通后台转换保留健康的 `AVPlayerItem` 和 layer 绑定。
- `didBecomeActive` 调用 `ensureAVPlayerPresentation`，仅在当前 item、surface、generation 都有效时修复 layer。
- AVPlayer PiP 有独立授权、请求、超时和 terminal delegate 状态。

### 5.2 推荐保持的生命周期

#### 后台播放开启

```text
willResignActive
→ 清理计时基线，取消未经授权的 PiP 准备
→ 不重建 AVPlayer，不替换 AVPlayerItem

didEnterBackground
→ inBackground=true
→ 继续音频
→ AVPlayer/AVFoundation 自主管理不可见视频呈现

didBecomeActive
→ 核对 generation/item/surface
→ ensureAVPlayerPresentation
→ 必要时重新绑定当前 AVPlayerLayer
```

#### 后台播放关闭

```text
didEnterBackground
→ 统一 BackgroundPlaybackPolicy 判定不允许
→ pause()
→ wantsPlayback=false
→ 回前台不自动恢复
```

#### AVPlayer PiP

继续使用现有独立 PiP 状态，不把普通后台音频误当成 PiP，也不为普通后台自动创建 PiP。

### 5.3 AVPlayer 审核结论

针对当前“media_kit 后台中断”问题，AVPlayer 主线不需要引入 `vid`、Flutter Texture 或 VideoOutput Dispose/Create。若在修复中同时改写 AVPlayer 输出生命周期，属于无必要扩大范围，会增加回归风险。

需要优化但不是当前根因的点：原生服务同样有 250 ms `tick()`。后台可以降为 1 秒左右或事件驱动，但必须保留睡眠定时、EOF、环境策略和必要进度更新的触发来源。

## 6. 播放线 B：media_kit/libmpv 策略

### 6.1 普通后台与 PiP必须是两种不同业务

| 类型 | 输出所有权是否转移 | 是否允许暂停音频 | 是否需要 Dispose/Create |
|---|---:|---:|---:|
| 普通后台音频 | 否，行内输出仍属于当前会话 | 否 | 首选不需要；失败时前台重建 |
| PiP | 是，从 Flutter Texture 交给 PiP renderer | 交接窗口可短暂暂停 | 需要 |
| 切换媒体/释放播放器 | 是，旧会话结束 | 允许 | 需要 |

现有 PiP 恢复逻辑包含 `pauseEngine()` 和 `presentationWaiting`，所以只能复用底层安全原语，不能直接作为普通后台流程调用。

### 6.2 推荐的普通后台状态机

```text
inlineActive
  | willResignActive
  v
inlineQuiescing
  | 原生 render gate 关闭 + worker barrier + glFinish
  v
inlineSuspended
  | didEnterBackground 且后台播放开启
  | 保存 vid + 设置 vid=no
  v
backgroundAudioOnly
  | didBecomeActive
  v
inlineResuming
  | 恢复 vid + 打开 render gate + 等待首个有效尺寸/帧
  +--------------------------> inlineActive
  |
  | 原地恢复超时/失败（仅前台）
  v
inlineRebuilding
  | Dispose + Create + 新 texture + 恢复 vid + 非零尺寸
  +--------------------------> inlineActive
  |
  | 重建失败
  v
foregroundAudioOnlyFailed（音频继续，显示“重试画面”）
```

### 6.3 为什么改为 suspend-first，而不是每次 Dispose

1. 普通后台没有第二个视频输出接管，不需要像 PiP 那样转移所有权。
2. 保留 `VideoController`、texture identity 和原生输出，可以显著降低回前台“有声音、无画面”的概率。
3. 控制中心、通知中心和系统弹窗也可能触发 `willResignActive`；suspend/resume 比完整销毁重建更快，用户不易看到黑屏。
4. 当前 `TextureHW.deinit` 会进入 EAGLContext 并释放 mpv render context。若等到 `didEnterBackground` 才 Dispose，可能在后台执行 OpenGL 清理，本身不安全。
5. 真正的安全要求是后台不再调用 GPU；原生 render gate、worker barrier 和 `glFinish` 能直接保证这一点。`vid=no` 再负责停止视频解码和帧生产。

### 6.4 进入后台的闭环顺序

#### `willResignActive`：安全闸必须同步生效

1. Swift 原生生命周期立即关闭该 engine/output generation 的 `renderingAllowed`。
2. 取消新的 resize、render、`textureFrameAvailable` 投递。
3. worker 队列执行 barrier，已开始的 OpenGL 工作完成 `glFinish`。
4. Dart 取消待创建的 VideoController/输出请求。
5. 不改变 `wantsPlayback`，不调用 `pauseEngine()`。

这一步即使最终只是打开控制中心也必须安全完成；回到 active 后可快速原地恢复。

#### `didEnterBackground`：决定播放策略

- 后台播放关闭：由现有统一策略调用 `pause()`，用户意图变为暂停；media_kit 输出保持 suspended，避免无意义视频解码。
- 后台播放开启、普通后台：保存实际 `vid`，设置 `vid=no`，进入 `backgroundAudioOnly`；音频继续。
- PiP 已经持有输出：不进入普通后台状态机，由 PiP 自己继续。
- 纯音频：没有 VideoController，跳过所有视频状态迁移。

原生 gate 必须独立于 Dart 回执。即使 Dart isolate 暂停、MethodChannel 超时或 `vid=no` 尚未返回，后台也不得进入 OpenGL。

### 6.5 返回前台的闭环顺序

1. `willEnterForeground` 只更新生命周期，不抢先恢复输出。
2. `didBecomeActive` 核对 engine ID、session generation、当前媒体和 PiP owner。
3. 若只是短暂 inactive 且未进入 background：直接打开原输出 gate，等待有效帧。
4. 若处于 `backgroundAudioOnly`：先恢复保存的 `vid`，再打开 render gate。
5. 观察首个有效视频尺寸/帧；成功后进入 `inlineActive`。
6. 超过短超时仍无帧，只在前台执行一次 Dispose/Create 重建：
   - 保留当前 Player、位置和播放意图；
   - 确认新 texture ID；
   - 恢复 `vid`；
   - 确认非零尺寸。
7. 重建仍失败：进入 `foregroundAudioOnlyFailed`，音频继续，UI 显示“画面恢复失败”和“重试画面”。

不能在普通恢复中重开媒体或 seek；只有最后的受控重建恢复才允许使用现有 checkpoint 事务，而且应作为最后手段。

### 6.6 独立的 UI 状态

必须新增与 PiP 无关的状态，例如：

- `inlineVideoState = active | suspended | resuming | rebuilding | failed`
- `videoRestoreAttempt`
- `videoRestoreDiagnostic`

这些状态不得复用：

- `presentationWaiting`
- `mediaKitPiPRestoring`
- `deferredMediaKitVideoRestore`
- “正在等待画中画结束”提示

普通画面恢复期间：

- 音频继续；
- Play/Pause、锁屏控制、上一首/下一首和音量继续可用；
- seek 原则上继续可用，但要由当前 session/generation 栅栏保护；
- PiP 按钮和视频轨相关操作暂时禁用；
- 300–500 ms 内可静默恢复；超过阈值显示轻量“正在恢复画面…”；
- 不应让用户等待现有 PiP 路径的 8–24 秒才得到反馈。

## 7. 逻辑闭环审核

### 7.1 核心状态矩阵

| 当前引擎 | 后台开关 | PiP | 进入后台 | 回前台 |
|---|---:|---:|---|---|
| AVPlayer | 开 | 否 | 音频继续；保留 item/layer 身份 | ensureAVPlayerPresentation |
| AVPlayer | 关 | 否 | 暂停并清除播放意图 | 保持暂停，恢复画面呈现 |
| AVPlayer | 任意 | 是 | AVKit PiP 继续 | 按 PiP terminal/restore 流程处理 |
| media_kit 视频 | 开 | 否 | 原生输出 suspend，`vid=no`，音频继续 | 原地恢复；失败才重建 |
| media_kit 视频 | 关 | 否 | suspend + 暂停 | 恢复画面但保持暂停 |
| media_kit 视频 | 任意 | 是 | PiP renderer 持有输出 | 独立 PiP Restore，不进入普通后台恢复 |
| media_kit 纯音频 | 开 | 不适用 | 音频继续，无视频动作 | 无视频恢复 |
| 任一引擎 | 任意 | 任意 | 中断/路由策略优先于后台策略 | 仅合法条件满足时恢复 |

该矩阵闭合了此前遗漏的“后台关闭也需要恢复静止画面但不能恢复播放”场景。

### 7.2 竞态闭环

每次异步操作必须同时验证：

- 当前 `engineKind`；
- `engineId`；
- `session generation`；
- `render transition generation`；
- 当前 `appPhase`；
- 当前 `presentationOwner`；
- 当前 `wantsPlayback` 只用于播放，不用于决定是否恢复静止画面。

关键竞态及出口：

| 竞态 | 处理 |
|---|---|
| 恢复中再次锁屏 | 立即关闭原生 gate；旧恢复回调因 transition generation 失效 |
| 后台中自动切下一集 | 新 engine 后台 headless open，默认无视频输出；回前台才挂载 |
| 恢复中用户切换媒体 | 旧 engine 回调只能清理自身，不能恢复旧 texture/vid |
| PiP 启动中进入后台 | presentation owner 由 PiP 请求状态决定；不能同时进入普通 audio-only 拆卸 |
| PiP 停止时仍在后台 | 回到 backgroundAudioOnly，不创建行内 texture |
| `didBecomeActive` 先于 Dart receipt | 原生状态保留 active 信号；Dart receipt 到达后重新评估，不能依赖一次性通知 |
| 设置在后台被关闭 | 立即暂停音频；不必创建画面 |
| 用户锁屏暂停后回前台 | 恢复画面呈现，但保持 paused |

### 7.3 失败闭环

| 失败点 | 失败出口 |
|---|---|
| `vid=no` 超时 | 原生 gate 已确保 GPU 安全；记录诊断，必要时安全暂停，不在后台重试 GPU |
| 原地恢复无帧 | 前台执行一次受控重建 |
| Dispose/Create 重建失败 | 音频继续，显示重试；不标记整个媒体致命失败 |
| AVAudioSession 激活失败 | 现有有界重试；耗尽后等待用户显式 Play |
| 当前媒体无音轨 | 暂停并给用户明确说明 |
| engine/session 已改变 | 丢弃旧回调，只清理旧资源 |

## 8. 操作闭环与用户卡点审核

### 8.1 当前方案中已发现的卡点

#### 卡点 A：复用 PiP `presentationWaiting`

现有代码在 `presentationWaiting` 时会阻止 `resumeEngine`，`attemptAudioRecovery` 会执行 `pauseEngine()`，UI 还会显示“正在等待画中画结束”。若普通后台恢复复用该状态，将直接违背“后台音频连续”。这是阻断项。

#### 卡点 B：24 秒恢复超时

现有 PiP Restore 的 Swift 超时是 24 秒，Dart 侧还可能等待 texture 与尺寸。这个等待窗口适合复杂 PiP 交接的兜底，不适合用户刚切回 App 的普通画面恢复。普通恢复必须使用更短的首帧阈值，并尽早给反馈。

#### 卡点 C：每次 inactive 都重建输出

用户拉下控制中心、查看通知或遇到系统弹窗后，App 可能没有真正进入后台。若一律 Dispose/Create，会带来不必要的黑屏和画面跳变。suspend-first 可以关闭 GPU 又避免重建。

#### 卡点 D：失败把整个会话判死

当前某些 PiP 恢复失败会进入 `media_playback_failed`。普通后台画面失败时音频可能仍然健康，不能把画面故障升级为媒体致命故障。

### 8.2 修订方案的用户体验出口

| 用户操作 | 是否有卡点 | 修订后的处理 |
|---|---|---|
| 锁屏后马上解锁 | 低 | 原地恢复旧输出，不重建；短时间内无提示 |
| 切其他 App 数分钟再回来 | 低 | 先恢复 `vid`；慢于阈值显示“正在恢复画面…” |
| 拉控制中心后返回 | 低 | 只 suspend/resume，不走 Dispose/Create |
| 回前台时用户按暂停 | 无 | 播放意图即时生效；画面仍恢复为暂停帧 |
| 回前台时用户拖动进度 | 可控 | session/generation 保护；允许 seek，不等待画面事务结束 |
| 恢复中切下一集 | 可控 | 旧事务作废；新媒体正常打开 |
| 画面恢复失败 | 有提示但不阻断音频 | 显示重试按钮，音频控制保持可用 |
| 后台播放关闭后返回 | 无误播 | 恢复画面但保持暂停 |

### 8.3 建议提示

- `正在恢复画面…`
- `音频正在播放，画面恢复失败`
- `重试画面`
- `此视频没有可用音轨，无法在后台继续播放`

这些提示需要进入本地化，不应复用 PiP 文案。

## 9. 是否能解决当前问题

### 9.1 能直接解决的部分

若按修订方案正确实现，可以直接消除当前最明确的高风险链路：

- 后台不再进入 `TextureHW.render()`；
- 已排队的 resize/render/frameAvailable 由原生 generation gate 丢弃；
- 后台视频轨设为 `vid=no`，停止不必要的视频解码；
- 250 ms media_kit 全量属性轮询降频/裁剪；
- 回前台优先复用旧输出，降低无画面回归概率；
- PiP 与普通后台拥有独立状态，不会相互暂停或错误恢复。

### 9.2 不能诚实保证的部分

静态方案不能保证：

- 所有 iOS/设备版本上 mpv 从 `vid=no` 恢复后都必然立即产出首帧；
- OpenGL worker barrier 的具体耗时和插件线程行为；
- 长时间后台、内存压力、蓝牙路由和系统中断的真实触发概率；
- 上游 media_kit 版本对本地补丁升级的兼容性。

因此最终结论只能是：**修订方案在逻辑上对准根因并形成失败出口，具备解决当前问题的充分设计条件；实际有效性必须由真机手工复现和系统终止日志确认。**

## 10. 推荐实施优先级

### P0：先完成安全闭环

1. 为 media_kit 插件增加 native render gate、worker barrier、`glFinish` 和 generation。
2. 新增独立的普通后台 `inlineVideoState`，不得复用 PiP 状态。
3. 实现 willResignActive suspend、didEnterBackground `vid=no`、didBecomeActive 原地恢复。
4. 确保普通后台流程不调用 `pauseEngine()`，除非后台播放关闭或安全闸无法确认。
5. 后台 media_kit 心跳改为最小属性集/低频。
6. 增加画面恢复失败的非致命状态和重试入口。

### P1：再做体验闭环

1. 普通恢复首帧延迟阈值和轻量提示。
2. 前台原地恢复失败后的单次 Dispose/Create 重建。
3. 统一“后台继续音频”文案和本地化。
4. AVPlayer 原生 250 ms tick 的后台降频。
5. 结构化诊断：engine、appPhase、owner、render state、generation、vid、首帧耗时、失败阶段。

### P2：真机手工验收

- AVPlayer MP4/MOV 与 media_kit MKV/WebM 对照。
- 内置扬声器、AirPods、蓝牙音箱、有线耳机。
- 锁屏、Home、App 切换、控制中心、通知中心、系统弹窗。
- 快速前后台往返、恢复中再次锁屏、自动切集、手动切集。
- PiP 启动/停止/失败与前后台交叉。
- 来电、Siri、闹钟、其他音频 App 抢占。
- 30–60 分钟后台播放并核对 Organizer/Devices 的 GPU、watchdog、CPU_FATAL、jetsam 日志。

## 11. 最终裁决

1. **当前问题真实存在，修复重点应限定在 media_kit 视频输出的后台安全。**
2. **AVPlayer 与 media_kit 是两条播放线，不能共用一套视频恢复命令。**
3. **原方案的“每次普通后台 Dispose/Create”可以工作，但回归和用户卡点偏高，不是最成熟选择。**
4. **推荐采用 suspend-first：普通后台保留 Controller/输出身份，关闭 GPU 与视频轨；回前台原地恢复，失败才重建。**
5. **普通后台状态必须与 PiP `presentationWaiting` 完全分离，否则逻辑不闭环。**
6. **按本报告补齐后，方案在静态设计层面闭环、操作层面有失败出口、用户层面没有必须等待 PiP 事务的硬卡点，可以进入实现阶段。**
7. **在真机验证完成前，不能宣称问题已经修复，只能宣称设计已覆盖已知根因。**

## 13. 文件修改记录

### 修改前

现有方案已经区分 AVPlayer 与 media_kit 两条播放线，并提出 media_kit 后台 Dispose/Create，但没有完整审计普通后台与现有 PiP 状态的冲突，也没有处理短暂 inactive、高达 24 秒的恢复等待及 Dispose 在后台触发 OpenGL 清理的风险。

### 修改后

新增本独立审核文档，重新梳理统一策略层与两条播放线，将 media_kit 普通后台调整为 suspend-first，并补充状态矩阵、竞态出口、失败出口、用户卡点、实施顺序和公正裁决。

### 修改内容

仅新增本文档；未修改播放器源码、配置、依赖或测试文件。

### 修改原因

确保后续实现前先完成逻辑闭环、操作闭环和用户体验闭环，避免修复后台中断时重新引入“有声音、无画面”或“恢复期间停音”的问题。

### 可能影响或注意事项

本文档本身不改变 App 行为。suspend-first 需要修改本地 media_kit_video 插件，未来升级上游依赖时必须重新合并并审计。方案的最终可靠性仍依赖实现后的真机手工验证。
