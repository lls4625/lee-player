> 2026-10-20后续决策：用户已确认先优化雷player课程库根目录、文件夹内容和设置页滚动性能，再为根目录与文件夹内容增加交互滚动条。完整实施顺序、修改边界和验收标准见 `docs/vibe/2026-10-20_19-12-42-雷player列表滚动性能与滚动条完整优化方案.md`。本文继续作为根因证据记录，不以方案文档替代静态事实。

## 1. 结论摘要

结论：**与参考文档描述的问题部分一致，但不是完全相同的“每个列表项使用完整 Liquid Glass 并各自捕获背景”结构。**

雷player 当前锁定 `liquid_glass_widgets 1.3.0`，全局使用 `GlassQuality.standard`。该质量档的普通玻璃控件走包内的 `LightweightLiquidGlass` Shader，而不是 premium 完整折射管线。页面也只有一个根 `AdaptiveLiquidGlassLayer`；从锁定版本源码看，文件列表项没有形成“每项一个独立完整背景捕获 Layer”。

但参考文档指出的另一半风险明确存在：设置页和文件列表均让多个玻璃 Shader 形状随滚动移动。文件列表每个可见项通常同时含卡片面、媒体图标和菜单按钮；设置页每个分组含大面积玻璃面，并叠加图标、按钮或开关。可见项越多，同帧需要绘制的移动玻璃形状越多，因此它很可能是当前卡顿的重要贡献因素。

此外发现一个独立且可由代码直接证明的性能问题：iOS 原生播放服务固定每 `0.25` 秒发布一次完整播放状态，Dart `LibraryPage` 对每次通知都执行整页 `setState`。这会让设置页和文件列表即使只是在滚动，也按约 4 Hz 额外重建整个页面。它与玻璃 Shader 的滚动绘制叠加，可能放大卡顿感，不能把现象只归因于参考文档中的 Layer 问题。

由于本次按约束未运行 App、构建、测试或性能采样，以上结论是静态代码证据，不等同于真机 Profile 已确认唯一根因。

## 3. 问题清单

### LG-ROLL-001：滚动项内存在多个随列表移动的玻璃 Shader

- 现象/预期：两个页面滚动有卡顿感；预期 Profile/Release 真机滚动稳定，无明显连续掉帧。
- 分类：待验证风险。
- 来源：既有实现；没有差异证据表明由本次变更新引入。
- 严重程度：中高，影响两个用户高频页面；是否达到发布阻断需以真机帧数据判断。
- 根因状态：已定位为高可信贡献因素，尚未证明是唯一或首要根因。
- 处理状态：方案已确定，待分阶段实施与真机验证。
- 验收结果：未执行。

证据：

1. `v3/lib/main.dart:14-20` 初始化玻璃 Shader，并把全局质量固定为 `GlassQuality.standard`。
2. `v3/lib/glass_ui.dart:39-66` 的 `LeiSurface` 使用 `GlassContainer` 绘制整块玻璃面；`v3/lib/glass_ui.dart:94-104` 的每个 `LeiMediaIcon` 也使用一个 `GlassContainer`。
3. `v3/lib/library_page.dart:1835-1898` 的每个文件行包含默认非 `flat` 的 `LeiGlassTile`、一个 `LeiMediaIcon` 和一个尾部 `LeiGlassMenu` 触发按钮；有进度时还会增加 `GlassProgressIndicator`。
4. `v3/lib/library_page.dart:1902-1944` 的每个网格项包含 `LeiSurface`、`LeiMediaIcon` 和菜单按钮。
5. `v3/lib/library_page.dart:1070-1099` 的每个设置分组以大面积 `LeiSurface` 为背景；组内又有媒体图标、按钮、开关等玻璃控件。
6. `v3/lib/library_page.dart:1409-1416` 的设置列表设置了约 `0.75` 屏高度的 `cacheExtent`。这会提前构建下一组复杂玻璃控件，能降低临界进入视口时的首次创建尖峰，但也扩大单次整页重建所覆盖的已创建子树。
7. `v3/lib/library_page.dart:2107-2139` 的文件列表使用 `SliverList`/`SliverGrid` 懒构建，说明总文件数不会让全部文件项同时绘制；主要压力更接近“同屏可见玻璃数 + 滚动时持续移动”，而非全部文件一次性布局。

与参考文档的差异：

- 当前依赖不是直接使用文档示例中的 `liquid_glass_renderer` API，而是上层组件库 `liquid_glass_widgets 1.3.0`。
- 锁定版本的 `GlassQuality.standard` 使用包内轻量 Shader；不是 premium 完整背景捕获、折射和色差管线。
- 页面由 `GlassScaffold`/`GlassPage` 提供一个根 `AdaptiveLiquidGlassLayer`。普通卡片和图标没有在应用代码中设置 `useOwnLayer: true`。
- `LeiGlassTile` 虽调用 `GlassListTile.standalone`，但锁定包源码在 standalone 分支创建 `GlassContainer` 时没有继续传入 `useOwnLayer: true`，而 `GlassContainer` 默认值为 `false`。按实际 1.3.0 源码，它仍落入共享上下文，不能据名称认定每行有独立 Layer。
- 页面提供静态渐变背景，`GlassPage` 默认启用一层背景采样边界；但普通 standard 列表玻璃走合成的轻量 Shader，未发现每项分别持有背景采样 key 的证据。

判断：参考文档中的“多个移动玻璃形状、同屏面积和数量增大造成 GPU 压力”适用于本项目；“每项完整 renderer、每项独立 Layer、多次背景捕获”不适用于当前静态证据。

### LG-ROLL-002：原生 4 Hz 状态心跳触发 LibraryPage 整页重建

- 现象/预期：滚动期间存在与滚动无关的周期性整页 rebuild；预期只让真正依赖播放进度的最小区域刷新。
- 分类：代码可证明缺陷；其对实际掉帧的占比仍待真机量化。
- 来源：既有实现；没有差异证据表明由本次变更新引入。
- 严重程度：中高，因为它同时作用于设置页和文件列表，并与多玻璃 Shader 绘制叠加。
- 根因状态：已定位。
- 处理状态：已获得方案制定授权；实施方案已确定，业务代码尚未修改。
- 验收结果：未执行。

完整触发链：

1. `v3/ios/Runner/PlaybackService.swift:1186-1188` 创建每 `0.25` 秒运行一次的主 RunLoop Timer。
2. `v3/ios/Runner/PlaybackService.swift:2422-2453` 的 `tick()` 无条件调用 `publish()`；这不以当前是否播放、是否位于播放页为前提。
3. `v3/ios/Runner/PlaybackService.swift:1294-1298` 的 `publish()` 增加 revision 并调用 `changed?(snapshot())`。
4. `v3/ios/Runner/PlayerBridge.swift:171` 把每次 changed 通过 EventChannel 发送为 `player` 事件。
5. `v3/lib/player_model.dart:221-273` 应用状态后对每个事件调用 `_notify()`。
6. `v3/lib/library_page.dart:228` 让 `LibraryPage` 监听整个 `PlayerModel`；`v3/lib/library_page.dart:264-266` 对每次通知直接 `setState(() {})`，从而重建从 `GlassScaffold` 到当前设置列表/文件列表的整页 Widget 树。

影响说明：Flutter rebuild 不一定等同于每个像素都重绘，但在滚动已经持续触发布局、合成和 Shader 绘制时，额外的周期性 Widget 构建和 RenderObject 更新会占用 UI 帧预算。文件项越复杂、设置页缓存的 section 越多，叠加成本越明显。

### LG-ROLL-004：语之初相对流畅与其滚动卡片主动降级有关

- 现象/预期：用户反馈语之初设置页相对雷player更流畅；预期统一语言选择样式时不把雷player的滚动性能问题复制到语之初。
- 分类：代码可证明实现差异；流畅度差距的实际占比仍待同机真机量化。
- 来源：两个项目既有实现差异。
- 严重程度：中高，直接影响后续UI统一方案。
- 根因状态：已定位为高可信解释因素，尚未证明是全部原因。
- 处理状态：方案已确定；雷player向轻量滚动表面策略靠拢，待实施及真机验证。
- 验收结果：未执行。

对比证据：

1. 语之初 `src/lib/glass_ui.dart:73-99` 的 `GlassSurface` 虽然给每个卡片建立自己的玻璃面，但 `StudyCard` 在 `src/lib/glass_ui.dart:545-565` 固定传入 `GlassQuality.minimal`。
2. 语之初 `_settings` 会在 minimal 卡片路径把 blur 降为 `0`；因此滚动卡片主动避开 standard Shader和实时模糊，视觉主要依靠 tint、边界和静态层次。
3. 雷player `v3/lib/main.dart:17-20` 全局采用 `GlassQuality.standard`；设置分组 `LeiSurface`、文件行 `GlassListTile`、媒体图标、菜单按钮、外观按钮及开关均默认继承 standard。
4. 雷player每个文件行通常至少包含卡片面、媒体图标和菜单触发器三个随列表移动的玻璃控件；语之初普通设置卡片主体为 minimal/blur 0，交互控件才保留更高质量。
5. 语之初 `PageBody` 当前是普通 `ListView` 且一次接收全部 children，并没有比雷player的 builder/sliver懒构建更占优势；它仍相对流畅，进一步支持“玻璃质量与同屏移动效果数量”比列表构建方式更值得优先验证。

判断：两个App统一多语言选择器时，只统一弹层组件不会解决雷player设置页滚动卡顿。语言弹层关闭后不参与页面持续滚动绘制。正确顺序应是先减少雷player滚动内容中的 standard玻璃面积/数量并隔离4 Hz整页刷新，再统一弹层交互；语之初现有滚动卡片的 minimal降级策略不应被反向升级成雷player当前的standard策略。

## 4. 建议的最小修复顺序

以下只是方案建议，本次没有实施：

1. 先隔离播放心跳刷新：让文件/设置页面只监听它实际依赖的状态，播放位置以更小的 `ListenableBuilder`/选择器或单独 notifier 更新，避免 4 Hz 整页 `setState`。这项不改变视觉，风险最小，也便于后续客观判断玻璃成本。
2. 再做 A/B：保持其他逻辑不变，把滚动项的大面积玻璃面和重复媒体图标临时替换成普通半透明 `DecoratedBox`，菜单/固定 AppBar 可保留完整玻璃。若 raster 掉帧显著下降，即可确认 LG-ROLL-001。
3. 正式视觉方案优先遵循参考文档：固定 AppBar/少量关键按钮保留玻璃；列表项卡片改静态模拟或包内更轻样式。不要先升级依赖或改成 premium，也不要给每项增加 `useOwnLayer: true`。
4. 设置页可评估减小或取消额外 `cacheExtent`，但应在第 1、2 步采样后决定；它可能在“提前构建”与“扩大重建子树”之间存在权衡，不能仅凭静态分析删除。
5. `GlassPage` 当前背景只是静态渐变，可单独 A/B `enableBackgroundSampling: false`；这可能减少一层背景采样开销，但不应预设它是主因。
6. 跨项目统一时复用语之初“内容卡片 minimal/blur 0、少量关键控件 standard”的分层原则；统一的是语义、布局和弹层交互，不要求滚动内容全部使用同档实时玻璃。

## 5. 固定验收场景与真机通过标准

需要在同一最终代码、同一设备、Profile 或 Release 模式下比较，Debug/模拟器结果不作为性能验收结论。

建议至少覆盖：

1. 设置页：从顶部连续快速滚到底，再慢速来回滚动 30 秒。
2. 文件夹列表布局：准备 100 个以上文件，至少 10 个含已播进度；连续快速滚到底并返回顶部。
3. 文件夹网格布局：同一数据重复场景 2。
4. 场景 1-3 分别在无播放、后台音频播放两种状态执行，用于识别 4 Hz 播放事件叠加影响。
5. iPhone 60 Hz 与 120 Hz 设备各至少一台；记录具体型号、iOS、构建号。

明确通过标准建议：

- Flutter Performance Overlay/DevTools 中，快速滚动期间 UI 与 Raster 帧均无成段超预算；按设备刷新率使用对应帧预算，60 Hz 为约 16.7 ms，120 Hz 为约 8.3 ms。
- Profile timeline 中不存在稳定约 250 ms 周期的整页 `LibraryPage` rebuild 尖峰。
- 文件数从少量增加到 100+ 后，因懒构建不应出现与总项目数近似线性增长的单帧构建时间。
- 去除列表项玻璃的 A/B 版本若明显更流畅，则正式修复应取得接近该版本的帧表现，同时保持文字、点击、菜单、进度、列表/网格切换及四语言可用。
