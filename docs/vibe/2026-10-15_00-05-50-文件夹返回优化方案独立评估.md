# 文件夹返回优化方案独立评估

## 最终评估结论

用户已确认不需要文件夹左侧滑动返回，因此评估对象收敛为“将现有返回按钮固定到顶部导航栏”。

该方案通过独立评估：针对当前问题，用户操作能够闭环；不会引入新的手势冲突、等待状态或明显卡顿；也没有发现新的永久卡住点。它是当前最小、最稳妥的方案。

## 用户操作是否闭环

### 文件夹浏览

操作链路为：

`课程库根目录 → 打开文件夹 → 浏览/滚动文件列表 → 点击固定返回按钮 → 返回父目录或根目录`

按钮始终位于 `GlassAppBar`，不受列表滚动位置影响。一级目录返回根目录，多级目录逐级返回，能够形成完整闭环。

### 最近播放和收藏

这两个页面当前也把返回入口放在滚动页头中。同步将它们的返回按钮和标题移到固定导航栏后，用户在长列表任意位置都能回到课程库。

### 设置页

设置页不属于本次问题范围，继续使用现有独立返回按钮和既有滑动逻辑，不与文件夹页面混用状态。

### 根目录

根目录没有内部上一级，因此不显示返回按钮。用户不会遇到一个“看得到但点击无效果”的空操作。

结论：上述主路径闭环，没有必须回到列表顶部的步骤。

## 是否会带来新的操作问题

### 不会引入手势冲突

文件夹页不新增边缘滑动识别，因此不会与纵向列表滚动、卡片点击、文件菜单或系统手势竞争，也不需要维护 pointer 状态、滑动阈值和取消逻辑。

### 不会出现菜单下方偷偷返回

本次不增加 `PopScope` 或新的系统返回拦截。顶部更多菜单展开时，其全屏透明遮罩继续优先接收点击；用户第一次点击菜单外区域只会关闭菜单，不会同时触发返回按钮。

### 不会产生异步等待

现有返回只是同步修改 `tab` 或 `folder`，不依赖磁盘扫描、导入任务、原生通道或播放状态。返回按钮不应因 `fileBusy`、`scanning` 或 `importing` 被禁用。

### 快速连续点击

每次真实点击仍只执行一次现有回调。用户连续点击可以连续返回多级，这与普通层级导航一致。因为没有返回动画和异步操作，不需要为了本次修改增加额外导航锁。

### 长标题

新增 leading 后标题空间缩小。`GlassAppBar` 会约束标题宽度，但实现时仍应显式设置单行省略，避免长文件夹名影响可读性。右侧设置和更多按钮不会被标题覆盖。

## 卡顿评估

### 本次不会新增明显性能开销

- 固定栏只增加一个已有样式的按钮；
- 原滚动区中的同一个按钮会被移除，控件总量没有实质增加；
- 没有每帧手势监听、拖动动画或额外路由动画；
- 父路径计算只是短字符串处理；
- 返回行为与当前顶部旧按钮完全相同。

### 既有的大目录刷新成本

切换 `folder` 后，`visible` 会重新过滤并排序列表。文件数量极大时可能出现短帧停顿，但当前旧返回按钮已经走同一逻辑，因此不是本次固定按钮产生的新问题。

如果后续真机发现大目录切换卡顿，应单独优化目录索引或排序缓存，不应在本次 UI 调整中加入延时或加载态。

## 状态卡住评估

### 导入和扫描

导入、扫描状态保存在 `PlayerModel`，返回父目录不会停止任务，也不需要等待任务完成。顶部返回按钮应一直保持可用，因此不会出现“任务进行中无法离开目录”的卡点。

### 当前目录失效

当前目录如果被刷新、移动或删除，页面可能暂时显示为空，但固定返回按钮仍能返回父级，所以不存在无法退出的永久卡住状态。自动校正失效路径可以作为未来增强，不是本次必需项。

### 滚动位置

当前 `CustomScrollView` 已使用 `PageStorageKey('library/$tab/$folder')`。只要实现时保留该 Key，从子目录返回后应继续恢复父目录原来的滚动位置，不需要增加新的 ScrollController 状态。

## 最小实施边界

建议只修改以下内容：

1. 仅在 `tab == 1`、`tab == 2` 或 `(tab == 0 && folder.isNotEmpty)` 时，在 `GlassAppBar.leading` 显示现有返回按钮，避免设置页与原有返回按钮重复；
2. `GlassAppBar.title` 显示当前文件夹名或当前标签页名称；
3. 复用现有返回回调，不增加新的异步流程；
4. 删除 `libraryHeader()` 中会随列表滚动的返回行；
5. 保留继续学习卡片、列表结构、`PageStorageKey` 和设置页现状。

明确不增加：

- 文件夹边缘滑动；
- 文件夹路由栈；
- 新的 `PopScope`；
- 手势状态字段；
- 返回动画等待；
- 导航锁；
- 文件模型或原生端修改。

## 修改前后记录

- 修改前：独立评估包含自定义边缘手势、系统返回拦截、导航锁和菜单控制等扩展风险。
- 修改后：依据用户确认，移除这些非必需内容，只评估固定顶部按钮的最小方案。
- 修改内容：重写评估结论、风险分析、性能分析和验收矩阵。
- 修改原因：固定按钮已满足核心需求，简化方案可以直接消除大部分潜在新问题。
- 可能影响：评估结论由“条件通过”调整为“通过”；实施范围显著缩小。
