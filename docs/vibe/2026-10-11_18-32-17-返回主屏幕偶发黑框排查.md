# 返回主屏幕偶发黑框排查

## 一、结论

附件录屏中的“黑框”不是桌面残留窗口、播放器崩溃或媒体解码失败，而是雷player进入非活跃状态时过早清空 `AVPlayerLayer.player`，导致 iOS 在应用缩回主屏幕以及再次展开应用的系统动画中捕获到了黑色播放器底板。

根因位于 `v3/ios/Runner/PlaybackService.swift`：

- `UIApplication.willResignActiveNotification` 到达后立即调用 `suspendAVPlayerPresentationForBackground(lifecycleTransition: true)`；
- 该方法先释放预创建的画中画控制器，再执行 `videoLayer.player = nil`；
- `PlayerSurface` 自身背景固定为黑色，因此视频图层被清空后，播放控件仍存在，但画面区域立刻变黑；
- iOS 的主屏幕缩放动画此时尚未结束，于是缩放中的雷player界面以黑色视频区域显示，形成录屏中的黑框；
- 返回 App 时只在 `didBecomeActiveNotification` 后重新绑定播放器，系统展开动画可能已经开始，因此也可能短暂显示相同黑色视频区域。

该现象主要影响走 AVPlayer 路径的视频。本次文件名为 `test01.mp4`，而当前代码不会主动把 MP4 分配给 media_kit，因此在没有发生 AVFoundation 解码回退的情况下，与上述 AVPlayer 生命周期路径完全吻合。

## 二、附件证据

### 1. 录屏信息

- 文件：`/Users/javalee/Downloads/ScreenRecording_10-11-2026 18-23-25_1.MP4`
- 时长：约 7.43 秒
- 视频：HEVC，1290 × 2796，约 59.2 fps
- 录屏中可以看到应用多次在播放页与主屏幕之间切换。

### 2. 逐帧现象

在约 2.7～4.5 秒片段中可以连续观察到：

1. 主屏幕进入雷player时，系统先展开带完整播放控件的黑色播放页；
2. 随后视频画面恢复，播放控件与进度仍连续存在；
3. 再次返回主屏幕时，视频画面先变黑，但标题、进度条、锁定、旋转、画中画等控件仍存在；
4. 这个黑色播放页再随 iOS 动画缩回雷player图标；
5. 动画结束后主屏幕正常，不存在持续悬浮的独立黑色窗口。

这些特征说明消失的是原生视频内容层，而不是整个 Flutter 页面或 App 窗口。

## 三、代码链路

### 1. 播放页面底层必然呈现黑色

`v3/ios/Runner/PlaybackService.swift` 中的 `PlayerSurface` 使用 `AVPlayerLayer` 作为根图层，并设置：

```swift
backgroundColor = .black
```

Flutter 播放页本身也使用黑色背景。因此只要 `AVPlayerLayer` 暂时不再绑定播放器，控件仍在，而画面区域会变成纯黑。

### 2. 进入非活跃状态时立即解绑视频图层

当前生命周期监听为：

```swift
notifications.append(center.addObserver(
  forName: UIApplication.willResignActiveNotification,
  object: nil,
  queue: .main
) { [weak self] _ in
  self?.suspendAVPlayerPresentationForBackground(lifecycleTransition: true)
})
```

随后执行：

```swift
discardAVPlayerPiP()
if let videoLayer = surface?.videoLayer, videoLayer.player === player {
  videoLayer.player = nil
}
avPlayerPresentationDetachedForBackground = true
```

`willResignActive` 表示 App 即将失去活动状态，并不表示界面已经从屏幕消失。它也可能由系统覆盖层等暂时性事件触发。Apple 给出的前台转后台顺序同样是先 `willResignActive`，之后才是 `didEnterBackground` 和系统快照。因此在这个通知中清空可见视频图层，必然存在被过渡动画捕获的时间窗口。

### 3. 恢复绑定发生得较晚

当前只在 `didBecomeActiveNotification` 中调用 `restoreAVPlayerPresentationAfterBackground()`。这意味着从桌面重新进入 App 时，应用窗口可能已经开始展开，但视频层还没有重新绑定并产出画面，因而会再次出现短暂黑框。

### 4. 引入背景

`git blame` 显示这组解绑逻辑来自提交 `ebe956c2`（2026-10-03）。代码注释表明其目的不是处理视频渲染，而是防止预创建的 `AVPictureInPictureController` 在 App 退到后台时被系统自动启动。

因此，本问题属于“阻止自动画中画”实现带来的显示时序副作用。

## 四、为什么表现为偶发

逻辑本身每次都会在 `willResignActive` 尝试解绑，但肉眼是否能看见取决于以下竞争时序：

- iOS 主屏幕动画何时读取或合成 App 当前画面；
- `AVPlayerLayer` 最后一帧在解绑后还能保留多久；
- 设备负载和 GPU 合成节奏；
- 从桌面返回时，`didBecomeActive`、重新绑定播放器与下一帧视频提交的先后顺序；
- 连续快速进出 App 时，系统是否复用上一张窗口快照。

所以用户看到的是“多次返回时偶尔出现”，但触发条件与当前生命周期代码一致。

## 五、建议修复方案

### 推荐方案：生命周期切换时保留 AVPlayerLayer 的播放器绑定

把“阻止自动画中画”和“清空视频图层”拆成两个职责：

1. 在 `willResignActive` 时仍然撤销未获授权的预创建画中画控制器，防止自动进入画中画；
2. 不在该时刻执行 `videoLayer.player = nil`，让 iOS 的主屏幕过渡动画继续使用最后一个可见视频画面；
3. 在 `didBecomeActive` 时重新准备手动画中画控制器；
4. 只在媒体切换、播放器销毁、明确的画中画交接失败等真正需要释放显示输出的路径中解绑 `AVPlayerLayer`。

这个方案直接消除黑框来源，又保留“画中画只能由用户点击启动”的业务规则。后台期间保留图层与播放器的对象关联，不等于后台继续渲染视频；实际是否继续播放仍由现有 `BackgroundPlaybackPolicy`、音频会话和系统生命周期共同控制。

### 不推荐方案 A：把解绑从 `willResignActive` 延后到 `didEnterBackground`

它可能减轻缩回动画中的黑框，但 Apple 会在进入后台后生成 App 快照，仍可能得到黑色任务切换卡片；不同系统版本的动画时序也可能继续暴露黑框，不能从根因上解决。

### 不推荐方案 B：增加固定延迟

例如延迟 300～500 毫秒解绑依赖设备和系统动画时长，会引入新的竞态，并且无法可靠覆盖从桌面返回的黑屏窗口。

### 备选方案：退出前覆盖静态视频帧

可以先抓取最后一帧并显示为占位图，再解绑播放器。这会增加截图、同步、HDR/色彩空间、内存和隐私处理复杂度；当前问题不需要采用该方案。

## 六、预计修改范围与风险

如后续确认实施，预计只需调整：

- `v3/ios/Runner/PlaybackService.swift`
  - 拆分 `suspendAVPlayerPresentationForBackground` 的画中画撤销与视频图层解绑职责；
  - 调整 `willResignActive` 和 `didBecomeActive` 的调用顺序；
  - 保留媒体替换、明确 PiP 失败/停止路径原有的安全清理约束。

需要重点注意：

- 不能重新引入“用户未点击画中画按钮却自动进入画中画”的旧问题；
- 不能破坏手动画中画开始、停止、恢复到 App 的握手；
- 需要分别检查 AVPlayer 与 media_kit 视频；本次根因直接落在 AVPlayer 路径，media_kit 不应被无关改动；
- 需要人工验证开启/关闭后台播放两种设置，以及播放中、暂停中、控制中心覆盖、锁屏、主屏幕往返和手动画中画。
